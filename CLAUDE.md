# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Expo + React Native + TypeScript app for **Nascente**, an offline-first Bible app (see `../CLAUDE.md` and `../.docs/` for product context). This package implements: a multi-step **onboarding** flow, **Supabase auth** (sign-in / sign-up / password reset), the **Reader** (offline bundled Bible) with **verse highlighting**, **reading plans** with progress tracking, a **Study** tab (highlights/notes/bookmarks, Pro-gated), AI study tools (**Explain, chapter summary, devotional** — Pro-gated), **settings**, and the design system. Word study and Ask/go-deeper are not built yet (see AI study tools section below and `.docs/ai-features.md`). Entry point is `src/index.ts` (which imports `expo-router/entry` then `./theme/config` to initialize Unistyles before anything renders). Routing is file-based via `expo-router` (`src/app/`). Uses pnpm as package manager.

**Free reading, Pro everything-else (2026-06 model — see `.docs/monetization-strategy.md`):** only **reading + search** are free (for the free translations). **Highlights, notes, bookmarks, reading plans, AI, and the Pro/classic translations are all Pro**, gated via `useIsPro()` → the paywall. A **free account** adds cross-device sync of reading progress/streak ("save your progress"), not feature unlocks. So the dominant gate across surfaces is **Pro**, not auth: the Reader verse tap, Study tab, Plans tab, and Home plans-slot all show a Pro lock (→ `/paywall`) for non-Pro users. (`SignInPromptCard` is now mostly legacy — `ProLockCard` is the Pro gate; see Component layers + the per-surface sections.)

## Architecture

### Path aliases

`@/*` maps to `src/*`, `@/assets/*` maps to `assets/*` (see `tsconfig.json`). Always import via `@/...`, never relative paths across top-level folders.

### Component layers (atomic design)

`src/components/` is split into `atoms/`, `molecules/`, `organisms/`, each with a barrel `index.ts` that re-exports named exports. When adding a component, add it to the matching folder's `index.ts`.

- **atoms**: primitive UI (`Text`, `Button`, `Input`, `Divider`, `Avatar`, `SafeAreaView`) — own their style variants (e.g. `Button` has `variant`/`size` props mapped to `StyleSheet.create` lookups). `SafeAreaView` is a thin `withUnistyles(...)` wrapper over `react-native-safe-area-context`'s so themed backgrounds stay theme-reactive — see the Styling section. **Prefer `Button` (`variant={BUTTON_VARIANTS.Ghost}`, `icon`/`iconPosition`) over raw `Pressable`/`TouchableOpacity` for tappable actions with an icon+label** — beyond consistency, this avoids the nested-pressable gesture bug where wrapping a whole `PressableCard`/`PressableScale` around inner `Pressable`s causes the outer gesture to swallow inner taps (the inner action never fires). When an action row has 2+ items, build them as an object array (`{ key, onPress, label, icon }[]`) and `.map()` to `Button`s rather than hand-writing each one (see `VerseActionSheet`, `VerseOfTheDayCard`).
- **molecules**: small compositions of atoms (e.g. `InputField`, `SocialButton`, `SettingsRow`, `OnboardingStepHeader`, `BackButton`, `AppModal`). `BackButton` is a floating top-left chevron that renders `null` when `router.canGoBack()` is false — used on the auth screens (which center their own content and don't use the titled `ScreenHeader`). `AppModal` is the **reusable dismissable dialog shell** — a centered card over a dimmed backdrop (RN `Modal`, fade), dismissable via backdrop tap + an optional close (X); takes arbitrary `children` with `showClose`/`dismissOnBackdrop` toggles. Use it for any centered dialog (confirm/info/upsell); for the slide-up sheet style use a gorhom bottom sheet instead (see `VerseActionSheet`). **`AppModal` wraps its content in its own `GestureHandlerRootView`** — mandatory because RN `Modal` renders in a separate native view hierarchy the app-root `GestureHandlerRootView` (in `_layout.tsx`) can't reach, so gesture-handler-based pressables inside it get **no touches** without one. Since `Button` is `pressto`'s `PressableScale` (gesture-handler-based), any `Button` inside a `Modal` is dead without this — the symptom is a `Button` (e.g. NoteEditorModal's Save) doing nothing while plain RN `Pressable`s in the same modal (backdrop/close-X) still work. Don't put a `Button` (or any GH pressable) inside a bare RN `Modal`; route it through `AppModal`. `AppModal` also wraps its card in `react-native-keyboard-controller`'s `KeyboardAvoidingView` so a modal with a focused field (e.g. `NoteEditorModal`) lifts above the keyboard. `KeyboardAwareScreen` is the **reusable keyboard-aware scroll body** (wraps rn-keyboard-controller's `KeyboardAwareScrollView` with the app's shared defaults: `keyboardShouldPersistTaps="handled"`, `keyboardDismissMode="interactive"`, `bottomOffset`, `flex`). Use it instead of hand-rolling `KeyboardAvoidingView` + `ScrollView` + `Platform` branching for any scrollable screen with inputs — pass `contentContainerStyle` for the screen's own centering/padding. All auth screens (root + onboarding copies) and the AI-plan generator use it; the six auth screens were migrated off their duplicated `KeyboardAvoidingView` blocks. **Requires the root `KeyboardProvider`** (mounted in `src/app/_layout.tsx`, just inside `GestureHandlerRootView`). `react-native-keyboard-controller` is a **native module** — needs `pod install` + a native rebuild (not Expo Go), like RevenueCat/Google-Signin. `SegmentedControl` is a generic themed pill-row filter (`segments`/`value`/`onChange`, generic over the key type) — first used to filter the Study tab.
- **organisms**: screen-level sections composed from atoms/molecules (e.g. `LoginCard`, `RegisterCard`, `ScreenHeader`, `ActivePlanCard`, `SuggestedPlanCard`, `SignInPromptCard`, `VerseActionSheet`, `UpsellModal`, `NoteEditorModal`). `SignInPromptCard` is the reusable account-gate card (whole card is the CTA) — legacy under the Pro-gated model; `ProLockCard` is its Pro-tier sibling (same shape, accent icon badge + title + description + a `pro`-variant CTA button) used on the Study tab, Plans tab, and Home plans-slot to gate Pro-only surfaces (taps → `/paywall`). `VerseActionSheet` is the **multi-action verse sheet** opened from a verse tap in the Reader — a real native gesture sheet via `@gorhom/bottom-sheet` (driven by a `visible` prop → `expand()`/`close()` on a ref; requires the `GestureHandlerRootView` mounted at the app root in `src/app/_layout.tsx`). It hosts all per-verse study actions: highlight color picker, bookmark toggle, and a note action. See Reader + Study tools. **All `@gorhom/bottom-sheet` organisms** (`VerseActionSheet`, `AiExplainSheet`, `ChapterSummarySheet`, `AiDevotionalSheet`) additionally force-close via `useFocusEffect(() => () => sheetRef.current?.close())` from `expo-router` — the sheet is screen-local UI and must not stay mounted-open when the user navigates to another tab/screen. Apply this to any new bottom sheet. See also the Styling section's `@gorhom/bottom-sheet` reactivity note for the theme-color pitfall these same components hit. `UpsellModal` is the **reusable Pro-upsell dialog** (composes `AppModal`: accent icon badge + title + description + `pro`-variant CTA) shown at tier-gated moments — currently the active-plan cap on the Plans tab/detail (see Reading plans). `NoteEditorModal` is the **verse-note editor** (composes `AppModal`: multiline field + save/delete), opened from the sheet's note action (see Study tools).

Screens (`src/app/**`) compose organisms/atoms directly; they hold screen logic (handlers, mutations) and delegate presentation to organisms.

### Route folders with co-located logic

When a screen's handlers/mutations grow beyond trivial, convert the route file into a folder so the logic can be extracted to a hook without leaving `src/app/`: `src/app/login.tsx` → `src/app/login/index.tsx` (the route, UI-only) + `src/app/login/use-login-screen.ts` (the extracted hook). Expo Router resolves `login/index.tsx` to the same `/login` route, so nothing else (e.g. `Stack.Screen name="login"` guards in `_layout.tsx`) needs to change. Use this pattern instead of growing `src/hooks/` with screen-specific hooks that aren't reused elsewhere — only promote a hook to `src/hooks/` if more than one screen needs it.

Both the route file and its co-located hook use **default export** in this pattern — the hook is exempted from the named-export convention below because it's screen-private, not a shared module imported by name from elsewhere.

**Caveat under `(tabs)`:** the `(tabs)` Tabs navigator auto-registers _every_ file directly in its folder as a screen, so a co-located hook placed directly under it would render as a phantom tab. Two ways to suppress it: (1) for a single file, register it with `href: null` in `(tabs)/_layout.tsx` — lightest; (2) give the tab a nested `_layout.tsx` with a `Stack`, which scopes route scanning away from the Tabs navigator so co-located `use-*-screen.ts` files (and sub-routes like `plans/[planId]/`) never become tabs. **Current layout:** the Home tab is the only bare file (`(tabs)/index.tsx`); its logic lives in `src/hooks/use-home-screen.ts` (outside `(tabs)/`) to avoid the phantom. `reader/`, `plans/`, and `settings/` each have a nested `Stack` `_layout.tsx`, so their co-located hooks and sub-routes are safe. Folders nested under a `Stack` (`login/`, `register/`, `forgot-password/`, the `onboarding/*` folders) don't hit this at all.

### Styling — react-native-unistyles

`src/theme/config.ts` calls `StyleSheet.configure` (the side effect that matters — it's imported once, by `src/index.ts`, before the router entry renders) and registers `UnistylesThemes`/`UnistylesBreakpoints` via module augmentation. It composes three themes — `light`, `dark`, `sepia` (sepia reuses the `light` shadows) — each built from shared tokens (`font`, `typography`, `spacing`/`gap`, `radius`, `zIndex`, `opacity`, `motion`, `highlights`) plus a per-theme `colors` and `shadows` pulled from `src/theme/colors.ts` / `shadows.ts`. Token files live individually in `src/theme/` (`font.ts`, `typography.ts`, `spacing.ts`, `radius.ts`, `z-index.ts`, `opacity.ts`, `motion.ts`, `colors.ts`, `shadows.ts`) — add new tokens to the relevant file and wire them into `sharedTokens`/the per-theme objects in `config.ts`.

Components style with `StyleSheet.create((theme) => ({...}))` from `react-native-unistyles`, never `react-native`'s `StyleSheet`. Color tokens are nested under `theme.colors.semantic.*` (e.g. `bgPrimary`, `bgSecondary`, `textPrimary`, `accent`, `accentSubtle`, `danger`) — components should read `theme.colors.semantic.X`, not the flat shadcn-style aliases (`primary`, `accent`, `muted`, etc.) that also exist on the color object for reference/legacy parity. Always pull tokens off `theme` (`theme.spacing[4]`, `theme.colors.semantic.bgPrimary`) rather than hardcoding values.

**The Babel plugin is mandatory.** `babel.config.js` registers `react-native-unistyles/plugin` (`root: 'src'`) — this is what binds native ShadowNodes so `UnistylesRuntime.setTheme()` repaints live. Without it, theme changes only apply after a full JS reload. The plugin must run _before_ React Compiler; we satisfy this by keeping React Compiler inside `babel-preset-expo` (the `experiments.reactCompiler` flag in `app.json`) and Unistyles at the top level — Babel runs top-level plugins before preset plugins. **Don't** also add `babel-plugin-react-compiler` manually (it would double-apply). After editing `babel.config.js` or fonts, restart Metro with a cache clear (`pnpm start -c`); font/`app.json` changes additionally need a native rebuild (`pnpm ios`).

**Reactivity model & third-party components.** Unistyles v3 updates styles natively without re-rendering React, but the plugin only auto-processes components imported from `react-native`. A themed style on a **third-party** component (e.g. `SafeAreaView` from `react-native-safe-area-context`, which wraps a native view, not RN's `View`) or on a **navigator options object** (`Tabs`/`Stack` `screenOptions`) will keep its first-render colors and won't switch theme live. Two patterns handle this:

- **SafeAreaView:** use the themed atom `src/components/atoms/SafeAreaView.tsx` (a `withUnistyles(...)` wrapper that subscribes to the runtime). Always import `SafeAreaView` from `@/components/atoms`, never from `react-native-safe-area-context` directly.
- **Navigator options:** subscribe to the theme name (`useThemeStore((s) => s.theme)`) and read colors via `UnistylesRuntime.getTheme(themeName)`, then build `screenOptions` from those — making the colors a real dependency so the options recompute on theme change (see `src/app/(tabs)/_layout.tsx`). A bare `useThemeStore` subscription alone isn't enough: React Compiler memoizes the options object as stable because `styles.X` is a stable reference.
- **Custom `color`-like props on plain leaf components** (a `lucide-react-native` icon, `ActivityIndicator`): these are plain objects handed once to the component — not Unistyles-processed, so `styles.X.color` (a proxied/shared-value-backed read from `StyleSheet.create`) freezes at first-render and never repaints on theme change. **Fix: wrap with `withUnistyles(Component, (theme, rt) => ({ color: theme.colors.semantic.X }))`** (module scope, once per component type) — the library's preferred pattern (zero extra re-renders, forwards refs) over `useUnistyles()`, which is the documented fallback only for cases `withUnistyles` can't cover (e.g. `Stack`/`Tabs` `screenOptions`, per the Navigator options bullet above). For a prop that depends on local component state (not just theme), use `uniProps={(theme) => ({...})}` per-instance instead of a static mapping.
- **Never wrap a Reanimated-internals-driven component with `withUnistyles`** (see the Reanimated section below for why) — this includes `@gorhom/bottom-sheet`'s `BottomSheet` and `pressto`'s `PressableScale` (used by `Card`/`PressableCard`, `StudyCard`, `ThemePreviewCard`, and anywhere else press-scale animation is used). **Fix:** don't wrap these. If the component needs no themed prop at all, just drop the wrapper (check first — `PressableCard`'s wrapper was dead weight, not receiving any themed prop). If it needs a themed `style`/prop, read the theme name reactively via `useThemeStore((s) => s.theme)` (a plain Zustand string subscription, not a shared-value proxy) + `UnistylesRuntime.getTheme(themeName)`, and pass plain derived style objects to the prop on the un-wrapped component. See `VerseActionSheet`, `AiExplainSheet`, `ChapterSummarySheet`, `AiDevotionalSheet` (BottomSheet) and `StudyCard` (PressableScale).

**Fonts.** Reader fonts are variable fonts (`Literata`, `Source Serif 4`) plus `Lato`, registered in `app.json` via the `expo-font` plugin and referenced in `src/theme/typography.ts` / `font.ts` by their **real family name (OpenType name ID 1)** — `'Literata'`, `'Source Serif 4'` (note the spaces), `'Lato'` — never the per-file PostScript name (`'Literata-Regular'`, `'SourceSerif4Roman-Regular'`). Referencing the PostScript name pins the font to its static 400 instance, and RN then synthesizes bogus names like `Literata-Regular_Medium` so `fontWeight` silently drops; referencing the family name lets `fontWeight` drive the variable `wght` axis (Lato is non-variable, weight 400 only). When inspecting a new font, read its name table to get the family name before wiring it up. Adding/renaming fonts means editing `app.json` + a native rebuild.

### Reanimated — shared values and render

**Never read a shared value's `.value` (or call `.get()`) synchronously in a component's render body.** This is the root cause of Reanimated's strict-mode `Reading from 'value' during component render` warning — it must only be read inside a worklet context: `useAnimatedStyle`, `useDerivedValue`, `withTiming`/`withSpring` callbacks, or a gesture handler. A real instance of this bug hit `SegmentedControl` (`src/components/molecules/SegmentedControl.tsx`): `SegmentItem` computed `const active = Math.round(progress.value) === index` directly in its render body to build `accessibilityState` — `progress` is a `useDerivedValue` shared value, so every mounted segment tripped the warning on every render (visible as multiple warnings firing together whenever a parent re-render cascaded down, e.g. a theme switch re-rendering an always-mounted `SegmentedControl` elsewhere in the app — the warning count matched the segment count exactly: 4 on the Study tab's filter, 2 inside `AiExplainSheet`'s mode toggle on the Reader tab). **Fix:** derive the JS-thread-safe value from a plain prop/state instead — here, the parent already computes `activeIndex` as a plain number (`segments.findIndex(...)`), so `SegmentItem` takes it as a prop and compares `activeIndex === index` rather than reading the shared value. When debugging this warning, get the **component stack from the terminal/Metro log** (not just the toast) — it names the exact offending component directly, which is far faster than guessing from mount/re-render patterns.

**This is a distinct issue from the `withUnistyles`-on-Reanimated-components gotcha in the Styling section above** — that one is about *forcing an extra re-render* on a component whose *internals* read shared values; this one is about *app code* reading a shared value directly in *its own* render body. Both produce the identical warning text, so don't assume a fix for one covers the other — check every `.value`/`.get()` call site outside a worklet, not just `withUnistyles` wrappers.

### Navigation headers

The app does **not** use React Navigation's built-in headers — stacks set `headerShown: false` (e.g. `src/app/(tabs)/settings/_layout.tsx`) and screens render the custom `ScreenHeader` organism (`src/components/organisms/ScreenHeader.tsx`: themed back chevron + centered title, top safe-area) instead. This keeps headers fully theme-reactive (the native nav header isn't a Unistyles surface) and consistent with the design system. Build new in-screen headers with `ScreenHeader`, not navigator `options.title`/`headerShown`.

### Auth flow — Supabase Auth

Layered: screens (`src/app/login/`, `src/app/register/`, `src/app/forgot-password/`) → `src/hooks/use-auth.ts` (React Query mutations/queries + Zustand writes) → `src/lib/supabase.ts` (`supabase.auth.*` calls directly — there is no service module for auth; Supabase's SDK _is_ the service layer).

- `src/lib/supabase.ts` creates the single `supabase` client via `createClient`, configured with `AsyncStorage` as the session storage, an explicit `storageKey` (exported as `AUTH_STORAGE_KEY = 'nascente-auth'`, pinned so logout can hard-purge the token by prefix instead of guessing the derived `sb-<ref>-auth-token` default), `autoRefreshToken: true`, `persistSession: true`. Supabase's client handles token persistence and refresh internally — there is no custom axios instance, manual token storage, or refresh-queue logic for auth.
- `useAuthStore` (`src/stores/auth.ts`, Zustand) holds `user` (an `AppUser`, see below), `isAuthenticated`, `isHydrated`. `hydrate()` calls `supabase.auth.getSession()` once on launch, then subscribes via `supabase.auth.onAuthStateChange` so any session change (refresh, sign-out, cross-tab) keeps the store in sync automatically — mutations don't need to manually push user state on top of what the listener already does, though `onSuccess` handlers in `use-auth.ts` call `setAuth` directly too so the UI updates without waiting on the listener's async round-trip.
- `src/app/_layout.tsx` calls `hydrate()` once via a `useHydrate` hook defined inline. While `!isHydrated` it renders `null` (holding the native splash screen, via `expo-splash-screen`'s `preventAutoHideAsync`); once hydrated, it renders the animated `SplashScreen` organism (`src/components/organisms/SplashScreen.tsx`) until it signals `onReady` (hides the native splash) and `onFinish` (flips local `splashDone` state). Only then does it mount the `Stack`.
- **Routing guards are keyed on onboarding, not auth.** The `Stack` has two `Stack.Protected` groups: one gated on `shouldShowOnboarding` (`FORCE_ONBOARDING` dev flag OR `!hasCompleted` from `useOnboardingStore`) showing `onboarding`; the other gated on `!shouldShowOnboarding` showing the app — `(tabs)`, `login`, `register`, `forgot-password` **together in one group**. So a signed-out guest still reaches `(tabs)` (initial route); `login`/`register`/`forgot-password` are optional screens pushed on top (e.g. from settings). Signing in/out does **not** swap the navigator — screens navigate explicitly (see redirect bullet). There is no auth-guard hook or redirect call in `_layout.tsx`.
- `useLogin`/`useRegister`/`useGoogleLogin` all call the corresponding `supabase.auth.*` method (`signInWithPassword`, `signUp`, `signInWithIdToken`), map the returned Supabase `User` to the app's `AppUser` via `toAppUser()` (`src/types/auth.ts`), then `setAuth` + `queryClient.setQueryData(authKeys.me, user)` in `onSuccess`.
- `useForgotPassword` calls `supabase.auth.resetPasswordForEmail(email, { redirectTo: 'nascenteapp://reset-password' })` — the `nascenteapp` scheme is registered in `app.json`. This only sends the email; there's no in-app reset-completion screen yet (the linked flow is out of scope until that's built).
- `useMockLogin` is a `__DEV__`-only escape hatch (wired into `src/app/login/`) that writes a hardcoded `AppUser` straight to the Zustand store and query cache, bypassing Supabase entirely — use this pattern for any other dev-only shortcuts.
- `useLogout` does three things in order: (1) clear the Zustand store + the whole React Query cache (instant UI flip to guest, no previous-user data lingering e.g. on the Plans tab); (2) best-effort `supabase.auth.signOut()` in a `try/catch` (remote revoke; throws for a mock-login user or offline); (3) **hard-purge** the persisted session — `AsyncStorage.multiRemove` of every key starting with `AUTH_STORAGE_KEY` (covers the session + its `-code-verifier` sibling). Step 3 is the real guarantee: a failed/offline remote sign-out can't leave a token for `hydrate()` to restore on relaunch.
- Google sign-in uses `@react-native-google-signin/google-signin` for the native dialog (configured once at module load in `use-auth.ts` from `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` / `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID` env vars), then exchanges the resulting ID token with Supabase via `signInWithIdToken({ provider: 'google', token })`. Apple Sign-In is wired up as a no-op handler (`handleAppleLogin` — TODO, not implemented) in both `login/use-login-screen.ts` and `register/use-register-screen.ts`.
- Email confirmation is currently **disabled** in the Supabase project, so `signUp` returns an active session immediately — there's no "check your email to confirm" step. If that setting changes, `useRegister`'s `onSuccess` needs to branch on whether `data.session` is null.
- **Redirect-on-success (because the navigator doesn't swap on auth):** the root `login/`/`register/` screens are reached as a guest from settings, pushed on top of `(tabs)`. Their hooks call a `goToApp()` on success — `router.canDismiss() ? router.dismissAll() : router.replace('/(tabs)/settings')` — which closes the pushed auth stack and lands back on settings (now showing the signed-in profile card). The dev `mockLogin` is wrapped the same way. The **onboarding** copies of these screens redirect to `/onboarding/welcome` instead (see Onboarding flow).
- **Root auth screens** (`login/`, `register/`, `forgot-password/`) follow the route-folder pattern, render a `BackButton` (so a guest who entered from settings can return), and cross-link: `LoginCard.onForgotPassword` → `/forgot-password`, login ⇄ register via `Link`. `useMockLogin` and Apple Sign-In (no-op TODO) are wired here and in the onboarding copies.

### Onboarding flow

First-run flow under `src/app/onboarding/` (gated by the `shouldShowOnboarding` guard; `hasCompleted` lives in `useOnboardingStore`, `src/stores/onboarding.ts`). Each step is a route-folder with a co-located `use-*-screen.ts` hook, and most steps use `OnboardingStepHeader` (progress dots + back). Sequence:

`language (1) → translation (2) → preferences (3) → account (4) → [register | login | forgot-password] → welcome → app`

- **account** (`onboarding/account/`) — "Sincronize seus dados": **Criar conta** → pushes the onboarding `register`; **Usar sem conta** → pushes `welcome` (guest). Caption notes an account can be created later in settings.
- **account/register, account/login, account/forgot-password** — reuse the same `RegisterCard` / `LoginCard` / `ForgotPasswordCard` organisms as the root auth screens, but their hooks redirect to `/onboarding/welcome` on success (existing-account users can cross-link register ⇄ login, and login → forgot-password, all within the onboarding stack since the root `/login` etc. aren't mounted during onboarding).
- **welcome** (`onboarding/welcome/`) — final celebratory screen (animated "sun" sunburst via `react-native-reanimated` + `react-native-svg`, twinkling stars, pulsing button glow). **Começar a ler** → `complete()` + `router.replace('/(tabs)')`; **Explorar planos de leitura** → `complete()` + `/(tabs)/plans`.

`complete()` is called only at the welcome CTA, so the onboarding stack stays mounted through account/register/welcome without a premature guard switch.

### Forms & validation

React Hook Form + Zod, wired through `@hookform/resolvers`. Schemas live in `src/schemas/` as factory functions (`createLoginSchema()`, not a static export) because validation messages call `translate(...)` and need to read the current i18n locale at schema-creation time, not at module-load time.

### i18n

`src/i18n/` wraps `i18n-js`. `src/i18n/index.ts` barrels `i18n.ts` (instance config) and `translate.ts` (helper). Initial locale is set in `src/app/_layout.tsx` from `expo-localization`'s `getLocales()`, with fallback enabled; the user's choice is persisted in `useLocaleStore` (`src/stores/locale.ts`), which writes `i18n.locale` on change/rehydrate. Translation keys live per-locale in `src/i18n/translations/{en,es,pt}.ts`; add new keys to all three.

**Two ways to translate — pick by whether the text must update on a live language switch:**

- **`useTranslate()` hook** (returns a `translate` function) in any component whose text must re-render when the user changes language. It subscribes to `useLocaleStore` and returns a **locale-keyed closure**. The closure's per-locale identity is deliberate: with the stable module-level `translate`, React Compiler memoizes `translate('constant-key')` call sites as pure (it can't see that the helper reads i18n's mutable locale) and the strings only refresh after a full reload. Do not "simplify" the hook back to returning the bare `translate`.
- **Raw `translate(...)`** (imported from `@/i18n`) only where a live switch can't happen at that point: module scope, Zod schema factories (recreated per render, so they pick up the current locale anyway), and the logged-out auth screens (unreachable from the in-app language switcher).

**Require-cycle rule:** import the i18n instance from `@/i18n/i18n` (the file), not the `@/i18n` barrel, in any module the barrel transitively imports — notably `src/stores/locale.ts`. The barrel re-exports `use-translate.ts`, which imports the locale store, so importing the barrel back from the store creates a `i18n → use-translate → locale → i18n` cycle.

### Data fetching

TanStack Query. `src/lib/query-client.ts` provides the single `queryClient` instance (provided via `QueryClientProvider` in `_layout.tsx`). Query keys are namespaced per domain as `const` objects (see `authKeys` in `use-auth.ts`) — follow that convention for new domains rather than inlining key arrays.

**Refetch on tab focus.** React Query's `refetchOnWindowFocus` is a no-op in React Native (no browser window), so a screen returned to via the bottom tabs serves stale cache and won't re-fetch on its own. For React-Query-backed screens that must reflect fresh server data on focus (e.g. the Plans list + Plan detail), call `useRefetchOnFocus(queryA, queryB, …)` (`src/hooks/use-refetch-on-focus.ts`) — it bridges expo-router's `useFocusEffect` to `query.refetch()`, refetching only **stale** queries (respecting each `staleTime`). This is the React-Query analogue of `useSyncOnFocus` (which covers the Zustand/sync-engine surfaces — Study/Reader/Home; see Sync).

### Backend — Supabase

`src/lib/supabase.ts` is the single Supabase client. **Auth**, the **reading-plan tables** (`reading_plans`, `reading_plan_days`, `user_reading_plans`, `user_reading_plan_completions` — see `.docs/data-model.md`), and the **`profiles` table** (subscription `tier`, with signup auto-provision + active-plan-cap triggers — see Subscription tier) are wired up, as are the **study-tools tables** (`highlights`, `notes`, `bookmarks` — now **LIVE**). The study tools remain **local-first** (the AsyncStorage Zustand stores are the source of truth) but now **sync** to those tables when signed in + online (offline-first, last-write-wins + soft-delete tombstones — see Study tools sync). Generated DB types live in `src/types/database.types.ts` (regenerate via the Supabase MCP `generate_typescript_types` after any DDL). **Reading plans are now offline-first too** (see Reading plans + Sync): `use-reading-plans.ts` reads/writes local Zustand stores synced to the reading-plan tables via `src/services/sync/reading-plans.ts` (catalog cache + enrollments status-merge + completions union), rather than calling `supabase.from(...)` directly. Completions stay the authoritative append-only log; `current_day`/`status`/`progress` are derived. Everything user-mutable (study tools, reading-progress, plans) is now local-first and mirrors to Supabase through the one sync engine; SQLite unification of all those local stores is the only deferred offline TODO (`.docs/notes.md`).

### Reading progress tracking (local-first)

`src/stores/reading-progress.ts` (persisted Zustand) is the on-device source of truth for the Home stats — no account required. `readChapters` (keyed `${bookId}:${chapter}`, translation-independent) and `readDays` (`YYYY-MM-DD`) are written by `markChapterRead(bookId, chapter)`, called from the Reader via an effect when a chapter's verses are on screen (which also stamps "read today" for the streak). `computeStreak()` returns consecutive reading days ending today or yesterday. ### Reading plans

Plans tab under `src/app/(tabs)/plans/` (nested `Stack`). Data layer is `src/hooks/use-reading-plans.ts` (`planKeys` namespace): `useActivePlans`, `useSuggestedPlans`, `useStartPlan`, `usePlanDetail(planId)`, `useMarkPlanDayComplete`, `useArchivePlan`. **Offline-first.** Plans are local-first like the study tools: the hooks keep their React Query surface + signatures + `planKeys`, but the `queryFn`s/`mutationFn`s read/write **local Zustand stores** (`src/stores/plan-{catalog,enrollments,completions}.ts`) synchronously and fire a background `syncAll` — reads work offline, writes apply instantly. `current_day`/`status`/`progress` are **derived** from the completion set (helpers in `plan-enrollments.ts`), never stored authoritative. Catalog is cached device-global after a first online pull. Sync (`src/services/sync/reading-plans.ts`): catalog pull → enrollments (status-merge: archived sticky-wins) → completions (append-only union). Enrollments start offline with a client uuid (`expo-crypto`). See the Sync section + `.docs/study-tools-sync.md` §11.

- **List** (`plans/index.tsx`): **non-Pro users get a `ProLockCard`** (plans are Pro → `/paywall`); Pro users get active + suggested sections. Tapping a card **body** (active or suggested) → plan detail; the suggested card's **"Começar" button** starts inline (subject to the 50-active cap).
- **Detail** (`plans/[planId]/`): serves both **preview** (not enrolled → days + "Começar") and **detail** (enrolled → day-by-day with completion checks + progress bar + "Remover plano" which archives). Reachable from the Plans tab and Home active-plan cards.
- **Progress model:** completions are the source of truth; `useMarkPlanDayComplete` records an idempotent completion (unique `(user_plan_id, day)`) locally; `current_day` (lowest uncompleted) + `status`→`completed`-when-full are **derived** on read. **One-way** (no un-marking). Two triggers, both calling the same mutation: a manual check on each detail day row (offline/paper fallback), and the Reader read-through CTA (primary — see Reader). The passive scroll-detector alternative was **considered and rejected** (completion is irreversible — see `.docs/plans-progress-tracking.md` §3.3). Full design: `.docs/plans-progress-tracking.md` (§6/§7, now ✅ offline-first) + `.docs/study-tools-sync.md` §11.
- **Active-plan cap (free/Pro tier):** `useStartPlan` enforces a per-tier limit on simultaneously-active plans — **free = 2, Pro = 50** (`ACTIVE_PLAN_LIMIT` in `src/types/subscription.ts`). Defense-in-depth: app pre-check counts the **local** active enrollments (offline-capable; tier from the profile cache), a DB `BEFORE INSERT OR UPDATE` trigger on `user_reading_plans` as the server backstop (raises `PLAN_LIMIT_REACHED` on push), and the hook normalizes both into a typed `PlanLimitError`. The trigger is dirty-replay-safe (an `upsert` of an already-active row short-circuits — no double-count). Both "Começar" handlers catch the error and open the shared `UpsellModal`, whose CTA now routes to the **paywall** (`router.push('/paywall')` — see Paywall + RevenueCat). Tier comes from `useTier()` (see Subscription tier).
- **AI plan generator (`plans/create/`):** a Pro user taps "Criar com IA" (a button in the Plans list header, `use-plans-screen.ts` → `handleCreateWithAi`) → the generator screen (topic/feeling input + example-prompt chips + a days slider). Flow is two-step with an in-memory `step` state (`input` → `preview`), co-located hook `use-create-plan-screen.ts`. `use-ai-plan-generate.ts` exposes two mutations: `useGenerateAiPlan` (calls the `ai-plan-generate` Edge Function → returns a **preview**, the metered step) and `useSaveAiPlan` (on confirm: inserts `reading_plans` (`owner_id = uid`, `is_ai_generated = true`) + `reading_plan_days` **directly via `supabase.from().insert()`** — RLS owner-scoped, book names for `ref_label` resolved client-side from the reader translation via `getBookName` — then `addOwnPlan` into the local catalog + auto-enrolls through the same enrollment/active-cap path as `useStartPlan`). **This is the one plan write that bypasses the sync engine** (the catalog is otherwise pull-only): own AI plans are inserted server-side then mirrored locally, and re-pulled on sync (`syncPlanCatalog` now pulls `owner_id is null OR owner_id = uid`). `plan-catalog.ts`'s `replaceCatalog` **preserves own-plans** so a curated-only pull can't clobber them, and `getCuratedPlans` **filters to `owner_id null`** so private AI plans surface only in "Planos ativos" (auto-enrolled), never "Sugeridos". **Metering:** generation charges two counters server-side at generation time (even if the preview is discarded) — the per-feature `ai_plan_usage` count (10/cycle) and the shared `ai_usage` dollar ceiling; either hit → 429 (`AI_PLAN_LIMIT_REACHED` / `COST_CEILING_REACHED`, both carrying a `resetAt` cycle-end date). The UI warns up front that generating counts against the quota, and on a quota hit shows a **plain informational notice** (an `AppModal`, not `UpsellModal`) — "out of AI credits, resets in N days" (`daysUntilReset(resetAt)`) — **not** a paywall route, since the user is already Pro and there's no buy-more-credits product yet (documented V2 add-on). The active-plan-cap-on-save case (Pro user at 50) reuses the same informational notice (remove a plan first), also non-upsell. **Retention:** private AI plans are reaped by a daily server cron (`purge-ai-plans`) once **not `active`** (removed/finished/un-enrolled) **and** inactive for **30 days** — in-progress plans are never touched. "Remover plano" stays archive-only (offline-safe, syncs); there's **no** immediate client hard-delete — the row is reaped by the cron later (cron-only by decision, to keep the offline-first flow intact). The generator screen shows a `aiPlan.retentionNote` line so users know removed/unused plans are deleted after 30 days. See `.docs/ai-features.md` §5, `data-model.md` → AI-plan purge, + the AI-generate section below.

### Subscription tier

Account tier (`free`/`pro`) is **server-side data**, the source of truth for feature gates. Under the **"free reading, Pro everything-else"** model (2026-06, see `.docs/monetization-strategy.md`) `useIsPro()` gates the **entire study/organization layer**: highlights, notes, bookmarks, reading plans, AI, and the Pro/classic translations. Only reading + search (free translations) and on-device reading progress/streak are free; a free account adds cross-device sync of that progress, not feature unlocks.

- **Backend:** a `public.profiles` table (`id` → `auth.users`, `tier account_tier`, RLS = select-own-only, **no client writes** — tier is billing-controlled). A signup trigger auto-provisions a `free` profile; the active-plan-cap trigger reads `tier` to pick the limit. See `.docs/data-model.md`.
- **App:** `src/hooks/use-profile.ts` — `useProfile()` (React Query, `profileKeys.me`, `enabled: isAuthenticated`), plus `useTier()` / `useIsPro()` selectors. A **missing profile degrades to `free`** (e.g. dev mock-login users with no Supabase row), so gates never hard-fail. Tier types + `PlanLimitError`/`ACTIVE_PLAN_LIMIT` live in `src/types/subscription.ts`.
- **Two read paths, deliberately:** `useTier()` returns the **`profiles.tier` enum** and is used for the numeric `ACTIVE_PLAN_LIMIT` lookup — it must match what the DB plan-cap trigger computes from the same column, so it stays `profiles.tier`-only. `useIsPro()` (boolean, for **all feature gating** — verse study actions, Study tab, Plans, Home plans-slot + Destaques stat, the Pro translations) is **RevenueCat `customerInfo` OR `profiles.tier === 'pro'`** — RevenueCat for instant unlock the moment a purchase completes, `profiles.tier` as the server-authoritative backstop. Under the "free reading, Pro everything-else" model this is the single gate that turns the study/organization layer on.
- **Billing = RevenueCat** (now wired — see Paywall + RevenueCat). The webhook flips `tier → 'pro'` server-side; until the RevenueCat dashboard/keys are configured, accounts stay `free`.

### Study tools (highlights, bookmarks, notes)

Three **study tools** ship today — **highlights**, **bookmarks**, **notes** — all **local-first and Pro-gated** (the Reader verse tap → paywall for non-Pro; the Study tab shows a `ProLockCard` for non-Pro). These are separate from the AI study tools (Explain/chapter-summary/devotional — see "AI study tools" below); word study and Ask/go-deeper are still deferred. Bookmarks and notes are deliberate clones of the highlights architecture; each follows the same five-part pattern: typed identity + key in `src/types/study.ts` → persisted per-user Zustand store → hooks in `src/hooks/use-*.ts` → an action in `VerseActionSheet` → an enriched entry in the Study tab. Architecture mirrors reading-progress (on-device now, sync later).

- **Types:** `src/types/study.ts` — `Highlight` (+ `HighlightColor`, palette keys match `theme.highlights`), `Bookmark` (plain per-verse toggle, no body), `Note` (`body: string`), each with a `<thing>Key(userId, bookId, chapter, verse)` helper. Verse reference is the canonical identity; `translationId` records origin.

- **Verse action sheet** (`VerseActionSheet`, a gorhom bottom sheet): one surface for all per-verse actions — the highlight color picker (6 + remove), a **bookmark** toggle (toggles in place, sheet stays open), and a **note** action that closes the sheet and opens the `NoteEditorModal`. - **Study tab** (`src/app/(tabs)/study/`, nested `Stack`): **non-Pro users get a `ProLockCard`** (→ `/paywall`); Pro users get a `SegmentedControl` filter (Tudo / Destaques / Notas / Marcadores) over one unified list of `StudyItem`s. `use-study-screen.ts` merges all three annotation types and **enriches** them with book name + verse text from `@/services/bible` via one `enrichItems` pass (verses/book name fetched once per unique translation+book+chapter), sorted canonically. ### Sync (offline-first)

Local-first user data syncs to Supabase via a layer **on top of** the AsyncStorage Zustand stores (the stores stay the local source of truth — this is **not** a SQLite migration; unifying persistence on SQLite is a future TODO in `.docs/notes.md`). Two models: the **study tools** (highlights/bookmarks/notes — LWW + tombstones) and **reading-progress** (append-only set-union). The engine lives in `src/services/sync/` and is mounted once by the headless `useSync()` hook (`src/hooks/use-sync.ts`) in `src/app/_layout.tsx`. Full design + diagrams: `.docs/study-tools-sync.md`.

- **Row sync metadata.** Each record (`Highlight`/`Bookmark`/`Note`) carries `SyncMeta` (`src/types/study.ts`): `updatedAt` (LWW key), `deletedAt` (tombstone), `dirty` (local change not yet pushed), `syncedAt`. **Deletes are soft** — `remove*` keeps the row and stamps `deletedAt`+`updatedAt`+`dirty` (so the delete syncs); writes clear `deletedAt` (un-tombstone) and set `dirty`. Selectors in `use-{highlights,bookmarks,notes}.ts` filter out tombstones, so the UI/Study-tab/Home count ignore them. **Bulk "clear all"** is a **per-type** action — a **list-footer** button on each of the three specific Study tabs (Highlights / Notes / Bookmarks), **not** on the mixed "All" tab (a single clear-all there would be ambiguous) → confirm `AppModal` → `clearAll{Highlights,Bookmarks,Notes}(userId)` on the matching store → the shared `softDeleteAllForUser` helper (`store-helpers.ts`), the batch analogue of `remove*`: it tombstones every live row for the user in one pass (never a hard wipe), so the deletion syncs. The store writes are reactive (the `useCurrentUser*` selectors re-derive), so the list refreshes on its own; the handler just fires `syncAll(userId)` to push the tombstones. The hook exposes `clearFilter: ClearableFilter | null` (the active clearable type when its list is non-empty, else null) — this both gates the footer/modal and narrows the i18n key off `'all'` so `clearAll.*.${clearFilter}` type-checks. (Bookmarks gained an `updatedAt` for this; a one-time `migrateSyncMeta` on rehydrate backfills legacy rows + marks them `dirty` so the existing local corpus uploads on first sync.)
- **Engine (`src/services/sync/`).** One generic `syncCollection<T>(descriptor, userId)` drives all three study tables (they share the verse-identity shape) via a `CollectionDescriptor` (table name + `toRemote`/`fromRemote` mappers + store seams). `run.ts`'s `syncAll(userId)` runs the three study collections **plus** reading-progress sequentially with an in-flight guard + queued re-run (overlapping triggers don't stampede). The store seams `applyPulled`/`applyPulledMany`/`markSynced` + the shared merge/prune helpers live in `store-helpers.ts`.
- **Push then pull.** Push first: upsert `dirty` rows (chunked) on `onConflict: 'user_id,book_id,chapter,verse'` (idempotent on verse identity), read back the server `updated_at`, and `markSynced` (clears `dirty`, re-anchors `updatedAt` to server time). Then pull: rows where `updated_at > cursor` (per-collection-per-user cursor in `useSyncMetaStore`, persist `nascente-sync-meta`), paginated, cursor advanced to the max **server** `updated_at` seen (resumable backfill). Push-before-pull means our own rows echo back as LWW ties (no flicker).
- **Conflict rule (LWW).** A pulled row wins **iff `incoming.updatedAt > local.updatedAt`** (else keep local; ties keep local). Because a write clears `deletedAt`, this one rule resolves edit-vs-edit, delete-vs-edit, and resurrect by newest server timestamp. `updated_at` is **server-authoritative** (column default + the `set_updated_at` BEFORE UPDATE trigger override any client value), which is the clock-skew mitigation.
- **Reading-progress (append-only).** `src/services/sync/reading-progress.ts` syncs `readChapters`+`readDays` with a simpler model — no tombstones/LWW/cursor. Push inserts the whole local set (`on conflict do nothing`); pull unions all rows in via the store's `mergeRemote`. The store is **device-global**, so a guest's progress unions up to the account on sign-in. See Reading progress tracking above + `.docs/study-tools-sync.md` §9.
- **Reading plans.** `src/services/sync/reading-plans.ts` syncs three local stores (catalog pull-only → enrollments status-merge LWW → completions append-only union; run in that FK order). Backs the offline-first `use-reading-plans.ts` hooks (see Reading plans). Because those hooks read store *snapshots* via React Query `queryFn`s (not reactive), `useSync` **invalidates `planKeys`** when a plan store changes (local write or pull) so the Plans screens re-derive. See `.docs/study-tools-sync.md` §11.
- **Triggers.** `useSync` (`use-sync.ts`) runs only when the stores + auth are hydrated AND a user is signed in (guest no-op). Fires on: sign-in / user-id change (also launch-with-session), app foreground (`AppState`), reconnect (`@react-native-community/netinfo` false→true edge), and a debounced local mutation (study `byKey`, reading-progress, or the plan stores). A separate `useSyncOnFocus` (same file, via `useFocusEffect`) pulls when a screen gains focus — mounted on the **Study tab**, **Reader**, **Home**, and **Plans** (list + detail) so an in-app tab switch re-pulls another device's changes (a tab switch does **not** fire `AppState` foreground). **Logout** (`useLogout`) calls `useSyncMetaStore.clearForUser(previousUserId)` so a re-login does a clean full re-pull; the per-user stores stay untouched (they filter by user id, so logout shows nothing) and any un-pushed `dirty` rows flush on next sign-in. (The catalog store is device-global — not cleared.)
- **Schema + purge.** The study tables + `user_reading_progress` are LIVE (`.docs/data-model.md`). Study tombstones are purged at a **90-day** retention window both server-side (`purge_study_tombstones` via the `purge-study-tombstones` `pg_cron` job, daily) and client-side (`pruneTombstones` on rehydrate, only dropping already-pushed tombstones).

## Conventions

- ESLint config (`eslint.config.js`) is `eslint-config-expo` flat config + Prettier + `eslint-plugin-react-compiler` (recommended ruleset is enforced — write components compatible with the React Compiler, e.g. no manual memoization workarounds it would conflict with).
- Prettier: single quotes, semicolons, 120 print width, ES5 trailing commas, LF line endings (`.prettierrc`).
- Components/hooks/services follow named exports (no default exports except Expo Router screens, which require default export, and their co-located screen-private hooks — see "Route folders with co-located logic" above).
