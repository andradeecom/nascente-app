# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Expo + React Native + TypeScript app for **Nascente**, an offline-first Bible app (see `../CLAUDE.md` and `../.docs/` for product context). This package implements: a multi-step **onboarding** flow, **Supabase auth** (sign-in / sign-up / password reset), the **Reader** (offline bundled Bible) with **verse highlighting**, **reading plans** with progress tracking, a **Study** tab (highlights/notes/bookmarks, Pro-gated), AI study tools (**Explain, chapter summary, devotional** — Pro-gated), **settings**, and the design system. Word study and Ask/go-deeper are not built yet (see AI study tools section below and `.docs/ai-features.md`). Entry point is `src/index.ts` (which imports `expo-router/entry` then `./theme/config` to initialize Unistyles before anything renders). Routing is file-based via `expo-router` (`src/app/`). Uses pnpm as package manager.

**Free reading, Pro everything-else (2026-06 model — see `.docs/monetization-strategy.md`):** only **reading + search** are free (for the free translations). **Highlights, notes, bookmarks, reading plans, AI, and the Pro/classic translations are all Pro**, gated via `useIsPro()` → the paywall. A **free account** adds cross-device sync of reading progress/streak ("save your progress"), not feature unlocks. So the dominant gate across surfaces is **Pro**, not auth: the Reader verse tap, Study tab, Plans tab, and Home plans-slot all show a Pro lock (→ `/paywall`) for non-Pro users. (`SignInPromptCard` is now mostly legacy — `ProLockCard` is the Pro gate; see Component layers + the per-surface sections.)

## Architecture

### Path aliases

`@/*` maps to `src/*`, `@/assets/*` maps to `assets/*` (see `tsconfig.json`). Always import via `@/...`, never relative paths across top-level folders.

### Component layers (atomic design)

`src/components/` is split into `atoms/`, `molecules/`, `organisms/`, each with a barrel `index.ts` that re-exports named exports. When adding a component, add it to the matching folder's `index.ts`.

- **atoms**: primitive UI (`Text`, `Button`, `Input`, `Divider`, `Avatar`, `SafeAreaView`) — own their style variants (e.g. `Button` has `variant`/`size` props mapped to `StyleSheet.create` lookups). `SafeAreaView` is a thin `withUnistyles(...)` wrapper over `react-native-safe-area-context`'s so themed backgrounds stay theme-reactive — see the Styling section. **Prefer `Button` (`variant={BUTTON_VARIANTS.Ghost}`, `icon`/`iconPosition`) over raw `Pressable`/`TouchableOpacity` for tappable actions with an icon+label** — beyond consistency, this avoids the nested-pressable gesture bug where wrapping a whole `PressableCard`/`PressableScale` around inner `Pressable`s causes the outer gesture to swallow inner taps (the inner action never fires). When an action row has 2+ items, build them as an object array (`{ key, onPress, label, icon }[]`) and `.map()` to `Button`s rather than hand-writing each one (see `VerseActionSheet`, `VerseOfTheDayCard`).
- **molecules**: small compositions of atoms (e.g. `InputField`, `SocialButton`, `SettingsRow`, `OnboardingStepHeader`, `BackButton`, `AppModal`). `BackButton` is a floating top-left chevron that renders `null` when `router.canGoBack()` is false — used on the auth screens (which center their own content and don't use the titled `ScreenHeader`). `AppModal` is the **reusable dismissable dialog shell** — a centered card over a dimmed backdrop (RN `Modal`, fade), dismissable via backdrop tap + an optional close (X); takes arbitrary `children` with `showClose`/`dismissOnBackdrop` toggles. Use it for any centered dialog (confirm/info/upsell); for the slide-up sheet style use a gorhom bottom sheet instead (see `VerseActionSheet`). **`AppModal` wraps its content in its own `GestureHandlerRootView`** — mandatory because RN `Modal` renders in a separate native view hierarchy the app-root `GestureHandlerRootView` (in `_layout.tsx`) can't reach, so gesture-handler-based pressables inside it get **no touches** without one. Since `Button` is `pressto`'s `PressableScale` (gesture-handler-based), any `Button` inside a `Modal` is dead without this — the symptom is a `Button` (e.g. NoteEditorModal's Save) doing nothing while plain RN `Pressable`s in the same modal (backdrop/close-X) still work. Don't put a `Button` (or any GH pressable) inside a bare RN `Modal`; route it through `AppModal`. `AppModal` also wraps its card in `react-native-keyboard-controller`'s `KeyboardAvoidingView` so a modal with a focused field (e.g. `NoteEditorModal`) lifts above the keyboard. `KeyboardAwareScreen` is the **reusable keyboard-aware scroll body** (wraps rn-keyboard-controller's `KeyboardAwareScrollView` with the app's shared defaults: `keyboardShouldPersistTaps="handled"`, `keyboardDismissMode="interactive"`, `bottomOffset`, `flex`). Use it instead of hand-rolling `KeyboardAvoidingView` + `ScrollView` + `Platform` branching for any scrollable screen with inputs — pass `contentContainerStyle` for the screen's own centering/padding. All auth screens (root + onboarding copies) and the AI-plan generator use it; the six auth screens were migrated off their duplicated `KeyboardAvoidingView` blocks. **Requires the root `KeyboardProvider`** (mounted in `src/app/_layout.tsx`, just inside `GestureHandlerRootView`). `react-native-keyboard-controller` is a **native module** — needs `pod install` + a native rebuild (not Expo Go), like RevenueCat/Google-Signin. `SegmentedControl` is a generic segmented control (`segments`/`value`/`onChange`, generic over the key type) — used to filter the Study tab and toggle the `AiExplainSheet` mode. It is now backed by **Expo UI**'s community drop-in (`@expo/ui/community/segmented-control`: native SwiftUI segmented `Picker` on iOS / Jetpack Compose on Android), keeping the same generic API; it no longer uses Reanimated. See "Expo UI" below. `Slider` (atom) is likewise backed by Expo UI's universal `Slider` (`@expo/ui`) — same step-index API (`steps`/`value`/`onChange`). `Switch` (atom, `src/components/atoms/Switch.tsx`) is a native toggle backed by Expo UI's **universal `Switch`** (`@expo/ui`, SwiftUI `Toggle` on iOS / Material `Switch` on Android); unlike the `community/*` drop-ins used by `Slider`/`SegmentedControl` it does **not** self-wrap in a `<Host>`, so the atom wraps it (once, at the boundary) with `matchContents` + theme-driven `colorScheme`/`seedColor` (the accent tint) — used for the profile screen's view/edit mode switch in the header. See "Expo UI" below.
- **organisms**: screen-level sections composed from atoms/molecules (e.g. `LoginCard`, `RegisterCard`, `ScreenHeader`, `ActivePlanCard`, `SuggestedPlanCard`, `SignInPromptCard`, `VerseActionSheet`, `UpsellModal`, `NoteEditorModal`). The three auth cards (`LoginCard`, `RegisterCard`, `ForgotPasswordCard`) render their outer surface as the `Card` molecule (`src/components/molecules/Card.tsx`) rather than a bare `View` — same reuse-first rule as everywhere else in the design system: prefer the shared `Card`/`PressableCard` surface over a new one-off styled `View` unless a card truly needs bespoke chrome. `Card`'s own default padding/radius (`spacing[5]`/`radius['2xl']`) is overridden via the `style` prop to match these cards' larger `spacing[6]`/`radius.xl` spec (auth cards are visually denser than the default card, and drop `Card`'s default `shadows.lg` in favor of the override style already carrying it, so no double-shadow). Only `Card`'s root is used — not `.Header`/`.Body`/`.Footer` — since these cards have a single flat vertical `gap` layout with a text header block + form + divider + socials, not the header/body/footer split. `RegisterCard` additionally renders a terms-of-service/privacy-policy footer row (tappable `Text`s → `Linking.openURL`, same `EXPO_PUBLIC_TERMS_URL`/`EXPO_PUBLIC_PRIVACY_URL` env-var pattern as the paywall's legal footer in `Paywall.tsx`) since account creation is the point that implies agreeing to those terms; `LoginCard`/`ForgotPasswordCard` don't need one. (The older `LoginFooter` organism with static, non-tappable `login.privacyPolicy`/`termsOfService` text is unrelated template leftover, not wired to any URL — don't confuse it with this pattern.) `SignInPromptCard` is the reusable account-gate card (whole card is the CTA) — legacy under the Pro-gated model; `ProLockCard` is its Pro-tier sibling (same shape, accent icon badge + title + description + a `pro`-variant CTA button) used on the Study tab, Plans tab, and Home plans-slot to gate Pro-only surfaces (taps → `/paywall`). `VerseActionSheet` is the **multi-action verse sheet** opened from a verse tap in the Reader — a real native gesture sheet via `@gorhom/bottom-sheet` (driven by a `visible` prop → `expand()`/`close()` on a ref; requires the `GestureHandlerRootView` mounted at the app root in `src/app/_layout.tsx`). It hosts all per-verse study actions: highlight color picker, bookmark toggle, and a note action. See Reader + Study tools. **All `@gorhom/bottom-sheet` organisms** (`VerseActionSheet`, `AiExplainSheet`, `ChapterSummarySheet`, `AiDevotionalSheet`) additionally force-close via `useFocusEffect(() => () => sheetRef.current?.close())` from `expo-router` — the sheet is screen-local UI and must not stay mounted-open when the user navigates to another tab/screen. Apply this to any new bottom sheet. See also the Styling section's `@gorhom/bottom-sheet` reactivity note for the theme-color pitfall these same components hit. `UpsellModal` is the **reusable Pro-upsell dialog** (composes `AppModal`: accent icon badge + title + description + `pro`-variant CTA) shown at tier-gated moments — currently the active-plan cap on the Plans tab/detail (see Reading plans). `NoteEditorModal` is the **verse-note editor** (composes `AppModal`: multiline field + save/delete), opened from the sheet's note action (see Study tools).

Screens (`src/app/**`) compose organisms/atoms directly; they hold screen logic (handlers, mutations) and delegate presentation to organisms.

### Route folders with co-located logic

When a screen's handlers/mutations grow beyond trivial, convert the route file into a folder so the logic can be extracted to a hook without leaving `src/app/`: `src/app/login.tsx` → `src/app/login/index.tsx` (the route, UI-only) + `src/app/login/use-login-screen.ts` (the extracted hook). Expo Router resolves `login/index.tsx` to the same `/login` route, so nothing else (e.g. `Stack.Screen name="login"` guards in `_layout.tsx`) needs to change. Use this pattern instead of growing `src/hooks/` with screen-specific hooks that aren't reused elsewhere — only promote a hook to `src/hooks/` if more than one screen needs it.

Both the route file and its co-located hook use **default export** in this pattern — the hook is exempted from the named-export convention below because it's screen-private, not a shared module imported by name from elsewhere.

**Caveat under `(tabs)`:** the `(tabs)` Tabs navigator auto-registers _every_ file directly in its folder as a screen, so a co-located hook placed directly under it would render as a phantom tab. Two ways to suppress it: (1) for a single file, register it with `href: null` in `(tabs)/_layout.tsx` — lightest; (2) give the tab a nested `_layout.tsx` with a `Stack`, which scopes route scanning away from the Tabs navigator so co-located `use-*-screen.ts` files (and sub-routes like `plans/[planId]/`) never become tabs. **Current layout:** the Home tab is the only bare file (`(tabs)/index.tsx`); its logic lives in `src/hooks/use-home-screen.ts` (outside `(tabs)/`) to avoid the phantom. `reader/`, `plans/`, and `settings/` each have a nested `Stack` `_layout.tsx`, so their co-located hooks and sub-routes are safe. Folders nested under a `Stack` (`login/`, `register/`, `forgot-password/`, the `onboarding/*` folders) don't hit this at all.

### Styling — react-native-unistyles

`src/theme/config.ts` calls `StyleSheet.configure` (the side effect that matters — it's imported once, by `src/index.ts`, before the router entry renders) and registers `UnistylesThemes`/`UnistylesBreakpoints` via module augmentation. It composes three themes — `light`, `dark`, `sepia` (sepia reuses the `light` shadows) — each built from shared tokens (`font`, `typography`, `spacing`/`gap`, `radius`, `zIndex`, `opacity`, `motion`, `highlights`) plus a per-theme `colors` and `shadows` pulled from `src/theme/colors.ts` / `shadows.ts`. Token files live individually in `src/theme/` (`font.ts`, `typography.ts`, `spacing.ts`, `radius.ts`, `z-index.ts`, `opacity.ts`, `motion.ts`, `colors.ts`, `shadows.ts`) — add new tokens to the relevant file and wire them into `sharedTokens`/the per-theme objects in `config.ts`.

Components style with `StyleSheet.create((theme) => ({...}))` from `react-native-unistyles`, never `react-native`'s `StyleSheet`. Color tokens are nested under `theme.colors.semantic.*` (e.g. `bgPrimary`, `bgSecondary`, `textPrimary`, `accent`, `accentSubtle`, `danger`) — components should read `theme.colors.semantic.X`, not the flat shadcn-style aliases (`primary`, `accent`, `muted`, etc.) that also exist on the color object for reference/legacy parity. Always pull tokens off `theme` (`theme.spacing[4]`, `theme.colors.semantic.bgPrimary`) rather than hardcoding values.

**The Babel plugin is mandatory.** `babel.config.js` registers `react-native-unistyles/plugin` (`root: 'src'`) — this is what binds native ShadowNodes so `UnistylesRuntime.setTheme()` repaints live. Without it, theme changes only apply after a full JS reload. The plugin must run _before_ React Compiler; we satisfy this by keeping React Compiler inside `babel-preset-expo` (the `experiments.reactCompiler` flag in `app.json`) and Unistyles at the top level — Babel runs top-level plugins before preset plugins. **Don't** also add `babel-plugin-react-compiler` manually (it would double-apply). After editing `babel.config.js` or fonts, restart Metro with a cache clear (`pnpm start -c`); font/`app.json` changes additionally need a native rebuild (`pnpm ios`).

**Reactivity model & third-party components.** Unistyles v3 updates styles natively without re-rendering React, but the plugin only auto-processes components imported from `react-native`. A themed style on a **third-party** component (e.g. `SafeAreaView` from `react-native-safe-area-context`, which wraps a native view, not RN's `View`) or on a **navigator options object** (`Tabs`/`Stack` `screenOptions`) will keep its first-render colors and won't switch theme live. Two patterns handle this:

- **SafeAreaView:** use the themed atom `src/components/atoms/SafeAreaView.tsx` (a `withUnistyles(...)` wrapper that subscribes to the runtime). Always import `SafeAreaView` from `@/components/atoms`, never from `react-native-safe-area-context` directly.
- **Navigator options:** subscribe to the theme name (`useThemeStore((s) => s.theme)`) and read colors via `UnistylesRuntime.getTheme(themeName)`, then build `screenOptions` from those — making the colors a real dependency so the options recompute on theme change (see `src/app/(tabs)/_layout.tsx`). A bare `useThemeStore` subscription alone isn't enough: React Compiler memoizes the options object as stable because `styles.X` is a stable reference.
- **Custom `color`-like props on plain leaf components** (a `lucide-react-native` icon, `ActivityIndicator`): these are plain objects handed once to the component — not Unistyles-processed, so `styles.X.color` (a proxied/shared-value-backed read from `StyleSheet.create`) freezes at first-render and never repaints on theme change. **Fix: wrap with `withUnistyles(Component, (theme, rt) => ({ color: theme.colors.semantic.X }))`** (module scope, once per component type) — the library's preferred pattern (zero extra re-renders, forwards refs) over `useUnistyles()`, which is the documented fallback only for cases `withUnistyles` can't cover (e.g. `Stack`/`Tabs` `screenOptions`, per the Navigator options bullet above). For a prop that depends on local component state (not just theme), use `uniProps={(theme) => ({...})}` per-instance instead of a static mapping.
- **Never wrap a Reanimated-internals-driven component with `withUnistyles`** (see the Reanimated section below for why) — this includes `@gorhom/bottom-sheet`'s `BottomSheet` and `pressto`'s `PressableScale` (used by `Card`/`PressableCard`, `StudyCard`, `ThemePreviewCard`, and anywhere else press-scale animation is used). **Fix:** don't wrap these. If the component needs no themed prop at all, just drop the wrapper (check first — `PressableCard`'s wrapper was dead weight, not receiving any themed prop). If it needs a themed `style`/prop, read the theme name reactively via `useThemeStore((s) => s.theme)` (a plain Zustand string subscription, not a shared-value proxy) + `UnistylesRuntime.getTheme(themeName)`, and pass plain derived style objects to the prop on the un-wrapped component. See `VerseActionSheet`, `AiExplainSheet`, `ChapterSummarySheet`, `AiDevotionalSheet` (BottomSheet) and `StudyCard` (PressableScale).

**Fonts.** Reader fonts are variable fonts (`Literata`, `Source Serif 4`) plus `Lato`, registered in `app.json` via the `expo-font` plugin and referenced in `src/theme/typography.ts` / `font.ts` by their **real family name (OpenType name ID 1)** — `'Literata'`, `'Source Serif 4'` (note the spaces), `'Lato'` — never the per-file PostScript name (`'Literata-Regular'`, `'SourceSerif4Roman-Regular'`). Referencing the PostScript name pins the font to its static 400 instance, and RN then synthesizes bogus names like `Literata-Regular_Medium` so `fontWeight` silently drops; referencing the family name lets `fontWeight` drive the variable `wght` axis (Lato is non-variable, weight 400 only). When inspecting a new font, read its name table to get the family name before wiring it up. Adding/renaming fonts means editing `app.json` + a native rebuild.

### Reanimated — shared values and render

**Never read a shared value's `.value` (or call `.get()`) synchronously in a component's render body.** This is the root cause of Reanimated's strict-mode `Reading from 'value' during component render` warning — it must only be read inside a worklet context: `useAnimatedStyle`, `useDerivedValue`, `withTiming`/`withSpring` callbacks, or a gesture handler. A real instance of this bug hit the **former** Reanimated-based `SegmentedControl` (since migrated to Expo UI — see "Expo UI"; the current file no longer uses Reanimated, but the pattern below still applies to any new Reanimated component): `SegmentItem` computed `const active = Math.round(progress.value) === index` directly in its render body to build `accessibilityState` — `progress` is a `useDerivedValue` shared value, so every mounted segment tripped the warning on every render (visible as multiple warnings firing together whenever a parent re-render cascaded down, e.g. a theme switch re-rendering an always-mounted `SegmentedControl` elsewhere in the app — the warning count matched the segment count exactly: 4 on the Study tab's filter, 2 inside `AiExplainSheet`'s mode toggle on the Reader tab). **Fix:** derive the JS-thread-safe value from a plain prop/state instead — here, the parent already computes `activeIndex` as a plain number (`segments.findIndex(...)`), so `SegmentItem` takes it as a prop and compares `activeIndex === index` rather than reading the shared value. When debugging this warning, get the **component stack from the terminal/Metro log** (not just the toast) — it names the exact offending component directly, which is far faster than guessing from mount/re-render patterns.

**This is a distinct issue from the `withUnistyles`-on-Reanimated-components gotcha in the Styling section above** — that one is about *forcing an extra re-render* on a component whose *internals* read shared values; this one is about *app code* reading a shared value directly in *its own* render body. Both produce the identical warning text, so don't assume a fix for one covers the other — check every `.value`/`.get()` call site outside a worklet, not just `withUnistyles` wrappers.

**Never put a Unistyles `styles.X` in an `Animated.View`/`Animated.Text` style array — use a plain (non-Unistyles) object for the static style instead.** Under Reanimated 4.5 + Unistyles 3.1 (Expo 57 / RN 0.86), a Unistyles-processed `styles.X` handed to a Reanimated `Animated.*` throws **`[Reanimated] Invalid value for "unistyles_<hash>": an empty object is not a valid style value`** — the Unistyles array entry resolves to `{}` before its ShadowNode binding populates (a pre-paint window), and Reanimated's style validator rejects the empty `unistyles_<hash>` marker. Note this **contradicts the Unistyles docs**, which bless `<Animated.View style={[styles.x, animatedStyle]} />` — that guidance predates this RN/Reanimated combo; in this app the array-with-Unistyles form throws, so use a plain object. Concretely: move the static style to a module-level plain `const` (typed `as const`) and pass `[plainObj, animatedStyle]`; keep Unistyles `styles.*` only on plain RN `View`/`Text`. If the static style needs a theme token, read it via `useAnimatedTheme()` (`react-native-unistyles/reanimated`) inside the `useAnimatedStyle` worklet rather than a `styles.X`. Real instances: `SplashScreen` (`flexFill`), `AnimatedSun` (`sunLayer`), `ShineButton` (`shineBand`) — the latter two hit this after the Expo 57 upgrade on the onboarding welcome screen.

**This also applies to `pressto`'s `PressableScale`** (Reanimated-based — used by `Button`, `PressableCard`, `StudyCard`, `PlanDayRow`, `ThemePreviewCard`, `LanguageOption`, `TranslationOption`, and directly in a few screens): a Unistyles `styles.X` reaching it throws the same error, because Unistyles' Babel plugin injects a `unistyles_<hash>` **marker prop** (the C++ ShadowNode binding) onto the processed style object, and on a non-Unistyles surface that marker never binds — it stays `{}` and Reanimated's validator rejects it. Components that build their own style via `UnistylesRuntime.getTheme(themeName)` already pass a **plain** object (safe): `StudyCard`, `PlanDayRow`, `ThemePreviewCard`, `LanguageOption`, `TranslationOption`. The trap is passing a Unistyles `styles.X` **through** — as the caller's `style` prop into `Button` (e.g. `ProLockCard`'s `styles.cta`, `VerseActionSheet`'s action buttons), or directly (`credits.tsx` did `<PressableScale style={styles.linkRow}>`).

**`StyleSheet.flatten` does NOT fix this** — it *preserves* the `unistyles_<hash>` marker (it's built to keep the C++ binding), so a flattened style still throws. You must produce a **truly plain** object with the marker removed. Two fixes in use:
- **`Button`** copies real style keys off the caller `style` via a local `toPlainStyle(input)` helper (recurses arrays, drops any `unistyles_*` key + function values), then spreads `{ ...containerStyle, ...toPlainStyle(style) }`. This covers **every** caller at the boundary, so call sites can keep passing a Unistyles `style`. Button re-derives on `themeName`, so themed caller overrides still refresh on a theme switch.
- **Direct `PressableScale` in a screen** (`credits.tsx`): define the style as a **plain module-level `const`** (import raw tokens like `spacing` from `@/theme/*` — spacing/radius are theme-independent), not a Unistyles `styles.X`.

Prefer routing tappable actions through `Button`/`PressableCard` (which handle this) over a bare `PressableScale` with a Unistyles style.

### Expo UI (native / glass UI)

We are progressively adopting **Expo UI** (`@expo/ui`, plus `expo-router/unstable-native-tabs`) to get a modern iOS **liquid-glass** look while rendering native Material controls on Android — design tokens still drive colors/labels. Every Expo UI native component **requires a dev/standalone build** (native module) — not Expo Go — and native surfaces are **not Unistyles surfaces**, so theme-reactive colors must be fed by subscribing to the theme name (`useThemeStore((s) => s.theme)`) + `UnistylesRuntime.getTheme(themeName)`, not inline `styles.X` reads (same caveat as navigator options). Full plan/candidate list: `.docs/design-system.md` → "Expo UI adoption" + `.docs/notes.md`.

- **`Slider`** (atom, `src/components/atoms/Slider.tsx`) → Expo UI **community drop-in** `Slider` (`@expo/ui/community/slider`: SwiftUI slider iOS / Material 3 Android). Keeps its original **step-index** API (`steps`/`value`/`onChange`); internally maps to `minimumValue=0`/`maximumValue=steps-1`/`step=1` and rounds the native fractional callback to an index. Accent via `minimumTrackTintColor` (iOS `.tint()`) + `thumbTintColor` (Android). Used by `FontSizeSlider` + the AI-plan day count. **Replaced a Reanimated + gesture-handler implementation that broke on Expo 57 / RN 0.86** (the `react-native-worklets` ABI shift). **Use the community drop-in, not the universal `@expo/ui` `Slider`:** the universal one renders a raw SwiftUI view **without a `<Host>`** wrapper, which logs a "wrap your component with `<Host>` from `@expo/ui/swift-ui`" warning and fails to lay out. The `@expo/ui/community/*` drop-ins (slider, segmented-control) each **self-wrap in the correct per-platform `Host`** (`matchContents={{ vertical: true }}`, `style` forwarded) — always prefer them over the universal components (which don't self-host) for standalone controls.
- **`SegmentedControl`** (molecule, `src/components/molecules/SegmentedControl.tsx`) → Expo UI **community drop-in** (`@expo/ui/community/segmented-control`: SwiftUI segmented `Picker` on iOS, Jetpack Compose `SingleChoiceSegmentedButtonRow` on Android/web). Keeps the generic `{ segments, value, onChange }` API; maps key ⇄ index at the boundary. **Theming quirk:** iOS ignores `tintColor` and follows the system light/dark, so we pass an explicit `appearance` (`dark` for the dark theme, else `light` — sepia → light) derived from the theme name; `tintColor` = accent applies on Android/web. Used by the Study filter + `AiExplainSheet` mode toggle. Also **replaced a Reanimated implementation** broken by Expo 57.
- **The Settings body is one native grouped list** → `SettingsGroup` molecule (folder `src/components/molecules/SettingsGroup/`: `index.ts` barrel + `.types.ts` + `.ios.tsx` + `.android.tsx` + `.tsx` base for TS/web resolution). The Settings screen keeps the custom `SettingsProfileCard` at top, then renders **all** other rows — Language + Theme (**picker** items) and Text size + Notifications + Credits + Support (**nav** items: label + optional trailing value + chevron, tappable) — inside a single native `SettingsGroup`. Items are a discriminated union (`{ type: 'picker' | 'nav', … }`) grouped into `sections`. This replaced the earlier `SettingsPickerGroup` cards + a separate `SettingsRow`/`SettingsList` card (the two lists looked mismatched, and the picker card floated in an ugly grey box). Key gotchas:
  - **One `<Host>`** wraps the whole group — the pickers/buttons must NOT self-wrap; `colorScheme` (+ iOS `seedColor` = accent) is driven from the app theme.
  - The universal `Picker` has **no `label`** prop (either platform) → iOS uses the **`@expo/ui/swift-ui` `Picker` with `label`** directly. **Android does not use the universal `Picker` at all** — its `TextField`-style anchor renders an un-themeable purple/blue pill (no color-override prop) — instead each Android picker row is hand-built from `DropdownMenu` + `DropdownMenuItem` (`@expo/ui/jetpack-compose`), both of which **do** support color overrides (`DropdownMenu`'s `color` for the popup, `DropdownMenuItem`'s `elementColors.textColor`), anchored by our own themed `Row` (label + value pill, `clickable` to expand).
  - **iOS fills the space** (`Host` `flex:1` + transparent bg + `useViewportSizeMeasurement`, `Form` `listStyle('insetGrouped')`) so the grouped background reads as the screen area below the profile card.
  - **Theming the native background (both platforms — the native grouped bg ignores Unistyles and clashes with sepia):** iOS hides the SwiftUI `Form`'s `.systemGrouped` background with **`scrollContentBackground('hidden')`** + a transparent `Host`, so the RN `SafeAreaView`'s `bgSecondary` shows through; row cards get **`listRowBackground(bgPrimary)`** (applied on `Section`). **Android does NOT use the universal `FieldGroup`** — its rows are hardcoded to Material `surfaceContainer` and can't be recolored — so the Android file builds the group from **themed Compose primitives**: a `Column` filled `background(bgSecondary)` containing rounded `Column` cards `background(bgPrimary)` + `clip(Shapes.RoundedCorner(20))`. Both then match every theme incl. sepia.
  - **Every Android `Text` needs an explicit `color` prop.** Unlike SwiftUI `Text` (which inherits a system label color that already tracked our `colorScheme`/`seedColor`), Jetpack Compose `Text` does **not** inherit Unistyles' text color — omitting `color` left every row's text unreadable (near-black) on the dark theme's dark card background. Pass `textPrimary`/`textSecondary` explicitly on every `Text` in the Android tree.
  - **Nav rows**: iOS = swift-ui `Button` (`buttonStyle('plain')`) wrapping `HStack(Text label, Spacer, Text value?, Image sf=chevron.right)`; Android = clickable Compose `Row` with a `'›'` `Text` (jetpack `Icon` needs a drawable `source`, not a name — no built-in Material-icon-by-name, so use a glyph).
  - `SettingsRow`/`SettingsList` are now unused by the Settings screen (kept in the repo for reuse). No universal *segmented* picker exists — that's why `SegmentedControl` uses the community drop-in.
  - **`Slider` (community drop-in) needs `maximumTrackTintColor` set on Android** (→ inactive track) — without it Material fills the rest of the track with a light-purple that clashes with the theme; we pass `bgTertiary`. The Text-size screen orders the slider first, then the preview card.
  - **`NativeTabs` needs `indicatorColor` on Android** — Material 3's active-tab indicator (the pill behind the selected icon) defaults to a fixed light `secondaryContainer`, ignoring the theme (wrong in dark/sepia); set it explicitly (e.g. `accentSubtle`) alongside `tintColor`/`iconColor`/`backgroundColor` in `(tabs)/_layout.tsx`.

#### Native tabs

The main bottom tabs (`src/app/(tabs)/_layout.tsx`) use **`NativeTabs`** from `expo-router/unstable-native-tabs`, not the JS-based React Navigation `Tabs`. This renders the **native system tab bar** — iOS gets the UIKit tab bar (and the iOS 26 **liquid-glass** effect automatically); Android gets the native Material tab bar.

- **Icons are platform-native, not the SVG set.** Each `<NativeTabs.Trigger.Icon>` takes `sf=` (SF Symbols) for iOS and `md=` (Material Symbols) for Android; pass `{ default, selected }` for a distinct filled selected glyph (iOS). The hand-drawn `src/components/atoms/TabIcons.tsx` SVG set is **no longer wired into the tab bar** (left in place, not deleted, in case it's reused elsewhere).
- **Theming: same non-Unistyles caveat as the old `screenOptions`.** The native tab bar is **not** a Unistyles surface, so it won't repaint on a live theme switch on its own. `_layout.tsx` subscribes to the theme name (`useThemeStore((s) => s.theme)`) and reads colors via `UnistylesRuntime.getTheme(themeName)`, then passes them to host props (`tintColor` = active accent, `iconColor`/`labelStyle` = inactive `textSecondary`) — making the colors a real dependency so they recompute on theme change (same rationale as the Navigator-options bullet in Styling; a bare subscription alone is memoized away).
- **The tab-bar chrome (glass appearance + background) is driven at the NATIVE level via `unstable_nativeProps`, NOT by `ThemeProvider`/`backgroundColor` — this is the real flash + stuck-light fix.** Root cause (traced in expo-router 57.0.4): on iOS the tab-bar `backgroundColor`/`iconColor`/`labelStyle`/`blurEffect` props are collected into screen options but then dropped — `createStandardAppearanceFromOptions`/`createScrollEdgeAppearanceFromOptions` (in `expo-router/.../native-tabs/appearance`) **return `{}`**, so only `tabBarTintColor` reaches native. With no explicit native appearance, the UITabBar falls back to the **device trait** (OS light/dark), and iOS swaps between the standard and (transparent) *scroll-edge* appearances on tab change → the bar ignored the app theme (app-in-dark + phone-in-light → light bar) **and** flickered. `ThemeProvider` (React Navigation `useTheme`) only themes the **screen content** background (`ScreenContent` in `NativeTabsView.shared`), not the bar chrome. The working levers are host-level `react-native-screens` `TabsHostProps`, reached via **`unstable_nativeProps`** on `<NativeTabs>`:
  - **`colorScheme: isDark ? 'dark' : 'light'`** — forces the `UITabBarController` trait to our app theme (fixes stuck-light-in-dark; sepia → light).
  - **`nativeContainerStyle: { backgroundColor: bgPrimary }`** — opaque themed fill on the tab-bar container view (kills the transparent flash).
  - Plus the first-class **`disableTransparentOnScrollEdge`** prop — stops the standard↔scroll-edge appearance swap (the flashing on scroll/tab change).
  We still keep the `backgroundColor`/`iconColor`/`labelStyle`/`tintColor` props (harmless, and they'd take effect if a future expo-router wires the appearance) and the `ThemeProvider` (root + tabs — it correctly themes screen-content backgrounds and transition scenes). Do **not** rely on `ThemeProvider` alone or on the `backgroundColor` prop for the bar in this expo-router version — they don't reach the native bar. Do **not** drive `ThemeProvider`/`colorScheme` from `useColorScheme()` (the docs' example) — that's the OS scheme, the exact mismatch. If a future SDK wires the appearance from options, this `unstable_nativeProps` block can be revisited.
- **Requires a dev/standalone build** (native module) — not available in Expo Go, like RevenueCat / Google-Signin / keyboard-controller.
- **Routing is unchanged.** `<NativeTabs.Trigger name="…">` maps to the same route names/nested `Stack` layouts (`reader/`, `plans/`, `settings/`) as before; the phantom-suppression rules in "Route folders with co-located logic" still apply (a stray file directly under `(tabs)/` would still register as a tab — suppress via a nested `_layout.tsx` `Stack` or a `hidden` trigger). The `unstable-` prefix means this API can shift in a future SDK.

### Navigation headers

The app does **not** use React Navigation's built-in headers — stacks set `headerShown: false` (e.g. `src/app/(tabs)/settings/_layout.tsx`) and screens render the custom `ScreenHeader` organism (`src/components/organisms/ScreenHeader.tsx`: themed back chevron + centered title, top safe-area, and an optional `right` slot for a top-right action — e.g. the profile screen's mode-toggle `Switch` — which falls back to a spacer that keeps the title centered) instead. This keeps headers fully theme-reactive (the native nav header isn't a Unistyles surface) and consistent with the design system. Build new in-screen headers with `ScreenHeader`, not navigator `options.title`/`headerShown`.

### Auth flow — Supabase Auth

Layered: screens (`src/app/login/`, `src/app/register/`, `src/app/forgot-password/`) → `src/hooks/use-auth.ts` (React Query mutations/queries + Zustand writes) → `src/lib/supabase.ts` (`supabase.auth.*` calls directly — there is no service module for auth; Supabase's SDK _is_ the service layer).

- `src/lib/supabase.ts` creates the single `supabase` client via `createClient`, configured with `AsyncStorage` as the session storage, an explicit `storageKey` (exported as `AUTH_STORAGE_KEY = 'nascente-auth'`, pinned so logout can hard-purge the token by prefix instead of guessing the derived `sb-<ref>-auth-token` default), `autoRefreshToken: true`, `persistSession: true`. Supabase's client handles token persistence and refresh internally — there is no custom axios instance, manual token storage, or refresh-queue logic for auth.
- `useAuthStore` (`src/stores/auth.ts`, Zustand) holds `user` (an `AppUser`, see below), `isAuthenticated`, `isHydrated`. `hydrate()` calls `supabase.auth.getSession()` once on launch, then subscribes via `supabase.auth.onAuthStateChange` so any session change (refresh, sign-out, cross-tab) keeps the store in sync automatically — mutations don't need to manually push user state on top of what the listener already does, though `onSuccess` handlers in `use-auth.ts` call `setAuth` directly too so the UI updates without waiting on the listener's async round-trip.
- `src/app/_layout.tsx` calls `hydrate()` once via a `useHydrate` hook defined inline. While `!isHydrated` it renders `null` (holding the native splash screen, via `expo-splash-screen`'s `preventAutoHideAsync`); once hydrated, it renders the animated `SplashScreen` organism (`src/components/organisms/SplashScreen.tsx`) until it signals `onReady` (hides the native splash) and `onFinish` (flips local `splashDone` state). Only then does it mount the `Stack`.
- **Routing guards are keyed on onboarding, not auth.** The `Stack` has two `Stack.Protected` groups: one gated on `shouldShowOnboarding` (`FORCE_ONBOARDING` dev flag OR `!hasCompleted` from `useOnboardingStore`) showing `onboarding`; the other gated on `!shouldShowOnboarding` showing the app — `(tabs)`, `login`, `register`, `forgot-password`, `reset-password`, `confirm-email` **together in one group**. So a signed-out guest still reaches `(tabs)` (initial route); `login`/`register`/`forgot-password` are optional screens pushed on top (e.g. from settings). Signing in/out does **not** swap the navigator — screens navigate explicitly (see redirect bullet). There is no auth-guard hook or redirect call in `_layout.tsx`.
- `useLogin`/`useRegister`/`useGoogleLogin` all call the corresponding `supabase.auth.*` method (`signInWithPassword`, `signUp`, `signInWithIdToken`), map the returned Supabase `User` to the app's `AppUser` via `toAppUser()` (`src/types/auth.ts`), then `setAuth` + `queryClient.setQueryData(authKeys.me, user)` in `onSuccess`.
- `useForgotPassword` calls `supabase.auth.resetPasswordForEmail(email, { redirectTo: 'nascenteapp://reset-password' })` — the `nascenteapp` scheme is registered in `app.json` (matches the bundle identifier convention). `src/app/reset-password/` is the completion screen — see "Auth-callback deep links (PKCE)" below for how it resolves the link before showing the form.
- `useMockLogin` is a `__DEV__`-only escape hatch (wired into `src/app/login/`) that writes a hardcoded `AppUser` straight to the Zustand store and query cache, bypassing Supabase entirely — use this pattern for any other dev-only shortcuts.
- **Profile editing** lives on the profile screen (`src/app/(tabs)/settings/profile/` — route-folder: `index.tsx` UI-only + `use-profile-screen.ts`). It has a **view mode** (avatar + name + email + sign-out) and an **edit mode** (name inputs + editable photo + save), toggled by a **native `Switch`** (`src/components/atoms/Switch.tsx`) in the `ScreenHeader`'s new `right` slot. `useUpdateProfile` (`use-auth.ts`) writes the editable fields (`firstName`/`lastName`/`profileImageUrl`) to Supabase auth **`user_metadata`** via `supabase.auth.updateUser({ data })`, then maps the returned user + pushes to store/cache in `onSuccess` (same pattern as the other auth mutations; the `onAuthStateChange` `USER_UPDATED` event also fires but we don't wait on it). **Email is display-only** — changing it triggers a re-confirmation flow with no in-app completion screen yet, so it's out of scope (shown disabled with a "can't be changed" hint). Name validation is a small zod factory (`src/schemas/profile.ts`), same factory-per-locale pattern as the auth schemas.
- **Avatar photo upload** goes through `src/lib/avatar-storage.ts` (`uploadAvatar(userId, localUri)`), the single seam for the **`avatars` Supabase Storage bucket** (public-read via the CDN URL; writes/updates/deletes RLS-restricted to objects under a `<uid>/` folder — the policy matches `(storage.foldername(name))[1] = auth.uid()`). **No SELECT policy** on `storage.objects` for this bucket — a public bucket serves reads via `getPublicUrl` with no policy, and adding a broad `using (bucket_id = 'avatars')` SELECT would also grant object **enumeration** (Supabase flags this: "clients can list all files in this bucket"), which we never need since avatars are only ever loaded by their known public URL. The picker is `expo-image-picker` (`launchImageLibraryAsync`, square crop; **native module** → needs the plugin in `app.json` + a dev/standalone build, not Expo Go — like Google-Signin/RevenueCat).
  - **Resize + recompress before upload** (`processAvatarImage`, via `expo-image-manipulator`'s SDK-57 builder API — `ImageManipulator.manipulate(uri).resize(...).renderAsync()` → `saveAsync({ compress, format: JPEG })`): the picker's `quality` only sets JPEG compression, **not pixel dimensions**, so a modern phone's 12+ MP photo stays multi-megabyte and can blow the bucket's 5 MB cap. We resize to a 512px square (well above the 96px `xl` Avatar even at 3x, tiny on disk — ~50–100 KB) — that's the real size lever. Normalizing to **JPEG** here also **subsumes format/HEIC handling**: whatever comes in (JPEG/PNG/WEBP, or an iOS HEIC) is decoded natively and re-encoded to JPEG, so the upload is always `.jpg`/`image/jpeg` and no mime-sniffing or HEIC-rejection guard is needed. (The picker is still set to `preferredAssetRepresentationMode: Compatible` as a cheaper first-line transcode, but the manipulator is the guarantee.)
  - Flow: pick → **local preview** (shown immediately, not yet uploaded) → **upload on save** (so cancelling edit costs no network and leaves no orphaned object). Upload reads the processed file straight to an `ArrayBuffer` via `expo-file-system`'s SDK-57 `File` class and hands it to `supabase.storage.upload()` (avoids the RN `Blob`/`FormData` upload pitfalls); the object path is `<uid>/avatar-<ts>.jpg` where `<uid>` comes from the **live session** (`getSession()`, not a caller-passed id) so it always matches the `auth.uid()` the RLS INSERT check keys on, and the timestamp cache-busts so a public URL never serves the stale previous photo. The resulting public URL is stored as `profileImageUrl` in `user_metadata`.
  - **Do NOT pass `upsert: true` to the upload** (gotcha, tied to the no-SELECT-policy decision above): `upsert` makes storage-api run a preflight **SELECT** to choose insert-vs-update, which requires a SELECT RLS policy on `storage.objects` — this bucket deliberately has none, so `upsert: true` fails with a **400 "new row violates row-level security"** even for a correctly-authenticated user on a correct path (a real bug we hit). The timestamped path never collides, so a plain insert is right anyway.
- `useLogout` does three things in order: (1) clear the Zustand store + the whole React Query cache (instant UI flip to guest, no previous-user data lingering e.g. on the Plans tab); (2) best-effort `supabase.auth.signOut()` in a `try/catch` (remote revoke; throws for a mock-login user or offline); (3) **hard-purge** the persisted session — `AsyncStorage.multiRemove` of every key starting with `AUTH_STORAGE_KEY` (covers the session + its `-code-verifier` sibling). Step 3 is the real guarantee: a failed/offline remote sign-out can't leave a token for `hydrate()` to restore on relaunch.
- Google sign-in uses `@react-native-google-signin/google-signin` for the native dialog (configured once at module load in `use-auth.ts` from `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` / `EXPO_PUBLIC_GOOGLE_IOS_CLIENT_ID` env vars), then exchanges the resulting ID token with Supabase via `signInWithIdToken({ provider: 'google', token })`. **The `webClientId` is the token audience and is required on BOTH platforms** (Android matches its OAuth client by package name + SHA-1, not by an ID passed in JS — `EXPO_PUBLIC_GOOGLE_ANDROID_CLIENT_ID` is intentionally unused). The iOS client additionally needs the `iosUrlScheme` (reversed iOS client ID) in `app.json`'s google-signin plugin config. Requires "Skip nonce checks" enabled on the Supabase Google provider (the lib sends no nonce).
- **Apple Sign-In is implemented** (`useAppleLogin` in `use-auth.ts`), mirroring the Google flow: `expo-apple-authentication`'s `signInAsync` (FULL_NAME + EMAIL scopes) → guard missing `identityToken` → `signInWithIdToken({ provider: 'apple', token })` → `toAppUser` → `setAuth` + cache. **First-sign-in name capture:** Apple returns `fullName` **only on the very first sign-in** and `signInWithIdToken` doesn't write it to metadata, so when present we persist `givenName`/`familyName` into our `firstName`/`lastName` `user_metadata` keys via `updateUser` (so `toAppUser` picks it up) — otherwise the account would have no name. `handleAppleLogin`/`handleAppleRegister` (in `login/`+`register/` screen hooks, root + onboarding copies) swallow the user-cancel case by **error `code === 'ERR_REQUEST_CANCELED'`** (cleaner than Google's cancel string-match) and otherwise toast. **iOS-only:** the Apple `SocialButton` is gated `Platform.OS === 'ios'` in `LoginCard`/`RegisterCard` because `expo-apple-authentication` isn't native on Android and `signInAsync` throws there (Supabase's Android-via-OAuth fallback is not wired). `expo-apple-authentication` is a config plugin (`app.json`) that adds the "Sign in with Apple" entitlement on prebuild → **needs a native rebuild + a real device/dev build** (not Expo Go), like Google-Signin/RevenueCat. Setup outside code (done 2026-07): App ID `com.andradee.nascenteapp` has "Sign in with Apple" enabled; a Services ID `com.andradee.nascenteapp.signin` (web-auth return URL = the Supabase `/auth/v1/callback`) and a Sign-in-with-Apple **Key** (`.p8`, Key ID `6M266N389V`) exist. **Supabase Apple provider config:** Client IDs = `com.andradee.nascenteapp,com.andradee.nascenteapp.signin` (bare bundle ID for the native token audience — **no `TeamID.` prefix** or native verification fails — plus the Services ID for web); "Allow users without an email" = **OFF** (native Apple always returns an email/private-relay, and `AppUser` assumes email exists). **The "Secret Key (for OAuth)" is a manually-generated ES256 JWT, NOT the `.p8` itself** — Supabase's single-field form doesn't build it from the key. Generator: `.docs/apple-secret.mjs` (zero-dep, Node `crypto`; reads the `.p8` next to it, prints the JWT). **Apple caps this secret at 6 months** — regenerate + repaste before it expires (current one expires **2027-01-15**) or web sign-in breaks silently. The `.p8` + token are secrets — `.docs/.gitignore` blocks `*.p8`; never commit either.
- **⚠️ Auth screens are TWO parallel copies — always change BOTH.** The root auth flow (`src/app/{login,register,forgot-password}/`) and the onboarding copies (`src/app/onboarding/account/{login,register,forgot-password}/`) each have their **own** co-located `use-*-screen.ts` hook. They share the same organism cards (`LoginCard`/`RegisterCard`/`ForgotPasswordCard`) but **not** the hooks — the only difference is the success redirect (`goToApp()` vs. `goToWelcome()` → `/onboarding/welcome`). So any auth-handler change (a new provider, an error-handling tweak, a cancel-case fix, the `needsConfirmation` branch) must be applied to **all four** screen hooks, or one entry point silently keeps the old behavior. Current handler status across all four: **email login/register ✅, Google ✅, Apple ✅** all wired; `handleAppleLogin`/`handleAppleRegister` are no longer TODO no-ops anywhere. When touching auth handlers, grep `handleGoogle|handleApple|useAppleLogin|useGoogleLogin` across `src/app` to confirm parity. (The Apple `SocialButton` is iOS-gated inside the cards, so both root + onboarding inherit that automatically — that part is NOT duplicated.) **Cancel-case detection differs by provider:** Google matches the thrown **message string** `'Google sign-in was cancelled'` (must stay in sync with the `throw` in `use-auth.ts`'s `useGoogleLogin` — fragile), Apple matches the error **`code === 'ERR_REQUEST_CANCELED'`** (sturdier — the model to follow for new providers).
- **Email confirmation is enabled.** `signUp` (`use-auth.ts`) passes `emailRedirectTo: 'nascenteapp://confirm-email'` and returns `{ user, needsConfirmation }`, where `needsConfirmation = data.session === null` — that's the only reliable signal `signUp` gives for "no session yet, check your email" (an already-registered email comes back the same shape). `onSuccess` only calls `setAuth`/caches the user when `!needsConfirmation`. Both register screens (root + onboarding, see the "TWO parallel copies" note below) hold the submitted email in local state and pass `needsConfirmation`/`submittedEmail` into `RegisterCard`, which swaps its form for a static "check your email" state (mirrors `ForgotPasswordCard`'s `isSubmitted` pattern) instead of navigating in. `src/app/confirm-email/` is the landing screen for the email link itself — see below.
- **Auth emails are rendered by our own edge function, not Supabase's templates** (`supabase/functions/send-email/`, a Supabase **"Send Email" Auth Hook**). Supabase's dashboard editor stores exactly one HTML body per email type, so it can't send pt/es/en variants — the hook intercepts before Supabase sends and renders branded, per-locale emails with **React Email**, delivered via **Resend's API**. Covers every `email_action_type` the app can trigger: `signup`, `invite`, `magiclink`, `recovery`, `email_change`, `email_change_new`, `reauthentication`. Three files: `index.ts` (verify → resolve locale → build URL → render → send), `AuthEmail.tsx` (the single branded template), `copy.ts` (all per-locale strings + `resolveLocale()` — **the only file to touch to reword an email or add a language**). Rationale + deploy checklist: `.docs/email-delivery.md`. Gotchas, each a real constraint:
  - **The hook resolves the email's language in this order: `?locale=` on the redirect → `user_metadata.locale` → `pt`.** The webhook payload carries no locale of its own, so the client has to supply it. **Both email-triggering calls in `use-auth.ts` append `?locale=` to their redirect** (`useRegister` → `emailRedirectTo`, `useForgotPassword` → `redirectTo`), which is the preferred signal because it's the language the device is in *at request time*. `useRegister` additionally stamps `user_metadata.locale` (and must do so **there**, not after — the confirmation email is sent by that very `signUp` call), which serves as the persistent fallback for any later server-triggered email. `setLocale` (`src/stores/locale.ts`) refreshes that metadata on language switches, best-effort/fire-and-forget.
    - **Why the redirect param is required, not just belt-and-braces:** `forgot-password` is a **signed-out** flow — there's no session, so `user_metadata` can't have been synced, and `resetPasswordForEmail` identifies the user by email alone. A real bug this fixed: switch to Spanish → log out → request a password reset → the email arrived in Portuguese (the signup-time value). The fire-and-forget metadata sync is also racy against `useLogout` revoking the session mid-write.
    - The callback screens (`confirm-email`, `reset-password`) destructure only `code`/`error`/`error_code`/`error_description` (see `AuthLinkParams`), so the extra `locale` param rides along harmlessly and never touches the PKCE exchange.
  - **A non-2xx response BLOCKS the auth operation.** Supabase does *not* fall back to its own mailer when the hook errors — a bug here breaks signup/password-reset entirely, not just the email. That's why unhandled action types (notification-only events) return **200 and skip** rather than erroring.
  - **Deploy with `--no-verify-jwt`.** The auth server authenticates with a Standard Webhooks signature, not a Supabase JWT, so `verify_jwt` rejects every call. The signature check in `index.ts` (over the **raw** body — read as `text()`, never `json()`, since the signature covers exact bytes) is the real auth gate.
  - **The clickable link is assembled by us** — the payload carries a `token_hash`, not a finished URL: `{SUPABASE_URL}/auth/v1/verify?token=…&type=…&redirect_to=…`, which consumes the token then bounces to the `nascenteapp://` deep link handled by the PKCE screens below.
  - **Copy lives in the function, not `src/i18n/translations/`** — these strings ship to the Deno edge runtime, not the device, and the app never renders them. Don't "consolidate" the two.
- **Auth-callback deep links (PKCE).** `src/lib/supabase.ts` sets `flowType: 'pkce'` explicitly (the SDK's default is `'implicit'`, which puts session tokens/errors in a URL **fragment** — `#access_token=...` / `#error=...`). This matters because **expo-router's deep-link parser drops URL fragments entirely** (`extractPathFromURL` only preserves the `?` query string), so under the implicit flow every Supabase auth email (signup confirmation, password reset, email change) would silently fail to deliver a session or a readable error to the app — links would land on `+not-found` with a mangled, double-encoded URL. PKCE redirects instead carry `?code=...` on success or `?error=...&error_code=...&error_description=...` on failure (e.g. `otp_expired` for a stale/already-used link) — both survive expo-router's query-string parsing. `src/lib/auth-link.ts`'s `resolveAuthLink(params)` is the shared resolver: exchanges `code` via `supabase.auth.exchangeCodeForSession()` (which saves the session and fires the `onAuthStateChange` listener itself — callers don't need to) or surfaces the error triple. Two screens use it:
  - **`src/app/confirm-email/`** — landing screen for the signup-confirmation link. States: resolving (spinner) → success (`CheckCircle2` + continue to `/(tabs)/settings`) → error (shared `AuthLinkErrorView` → back to `/login`).
  - **`src/app/reset-password/`** — same resolve-then-branch shape, but on success shows `ResetPasswordCard` (the actual new-password form) instead of a static success state; `useResetPassword` (`use-auth.ts`) then calls `supabase.auth.updateUser({ password })` against the session `exchangeCodeForSession` just established. On error, `AuthLinkErrorView` routes back to `/forgot-password` to request a new link.
  - **`AuthLinkErrorView`** (organism) is the shared "this link is expired/invalid" presentation — icon badge + title + description + single CTA — callers own the copy and the recovery action.
  - **`useLocalSearchParams` returns a new object identity every render — never depend on the whole object in an effect that exchanges a PKCE code.** A PKCE auth code is single-use; re-running the exchange (e.g. because an effect's deps array included the unstable `params` object) fails the second call even though nothing actually changed, and can look exactly like a fast/bogus "expired link." Both `confirm-email`'s and `reset-password`'s hooks destructure the scalar fields (`code`, `error`, `error_code`, `error_description`) as the real deps, plus a `resolvedRef` guard so the exchange can only fire once per mount. This satisfies `react-hooks/exhaustive-deps` for real (no disable comment) — a bare `eslint-disable` here trips **`react-compiler/react-compiler`**, which refuses to optimize a component with a suppressed React-rules lint.
  - **WebCrypto polyfill (`react-native-quick-crypto`).** Hermes has no native `crypto.subtle`, which `auth-js`'s PKCE code-challenge step needs (`crypto.subtle.digest('SHA-256', ...)`). Without it, `generatePKCEChallenge` silently falls back to `code_challenge_method=plain` (the raw verifier sent as the challenge — no hashing at all) and logs "WebCrypto API is not supported." `src/lib/supabase.ts` imports `react-native-quick-crypto` and calls `QuickCrypto.install()` (polyfills `global.crypto` + `global.Buffer`) before `createClient`, fixing this properly rather than accepting the `plain` fallback. **Requires `expo-build-properties`** as a peer dependency — the package's Expo config plugin (`app.plugin.js` → `withXCode`, registered in `app.json`'s `plugins`) imports it directly to bump the iOS deployment target; without it installed, the plugin fails to load (surfaces as a confusing `INVALID_PLUGIN_IMPORT`/parse-error diagnostic, not a clear "missing dependency" message). Native module — needs a rebuild (`npx expo prebuild` + `pnpm ios`/`pnpm android`), not Expo Go, like RevenueCat/Google-Signin/keyboard-controller.
  - **`src/app/+not-found.tsx`** is the catch-all for anything that isn't a matched route (mistyped in-app links, or a deep link that somehow still fails to parse) — distinct from the auth-error screens above, which handle the *expected* expired/invalid-link case with context-appropriate copy and a real recovery CTA.
- **Redirect-on-success (because the navigator doesn't swap on auth):** the root `login/`/`register/` screens are reached as a guest from settings, pushed on top of `(tabs)`. Their hooks call a `goToApp()` on success — `router.canDismiss() ? router.dismissAll() : router.replace('/(tabs)/settings')` — which closes the pushed auth stack and lands back on settings (now showing the signed-in profile card). The dev `mockLogin` is wrapped the same way. The **onboarding** copies of these screens redirect to `/onboarding/welcome` instead (see Onboarding flow).
- **Root auth screens** (`login/`, `register/`, `forgot-password/`) follow the route-folder pattern, render a `BackButton` (so a guest who entered from settings can return), and cross-link: `LoginCard.onForgotPassword` → `/forgot-password`, login ⇄ register via `Link`. `useMockLogin`, Google, and Apple Sign-In are all wired here and in the onboarding copies.

### i18n

`src/i18n/` wraps `i18n-js`. `src/i18n/index.ts` barrels `i18n.ts` (instance config) and `translate.ts` (helper). Initial locale is set in `src/app/_layout.tsx` from `expo-localization`'s `getLocales()`, with fallback enabled; the user's choice is persisted in `useLocaleStore` (`src/stores/locale.ts`), which writes `i18n.locale` on change/rehydrate. Translation keys live per-locale in `src/i18n/translations/{en,es,pt}.ts`; add new keys to all three.

**Auth *emails* are translated separately** — their copy lives in `supabase/functions/send-email/copy.ts` (edge runtime), not here. Adding a locale to the app therefore means adding it in **both** places, and the two aren't wired together by design (different build targets; see the send-email bullet under Auth flow).

**Two ways to translate — pick by whether the text must update on a live language switch:**

- **`useTranslate()` hook** (returns a `translate` function) in any component whose text must re-render when the user changes language. It subscribes to `useLocaleStore` and returns a **locale-keyed closure**. The closure's per-locale identity is deliberate: with the stable module-level `translate`, React Compiler memoizes `translate('constant-key')` call sites as pure (it can't see that the helper reads i18n's mutable locale) and the strings only refresh after a full reload. Do not "simplify" the hook back to returning the bare `translate`.
- **Raw `translate(...)`** (imported from `@/i18n`) only where a live switch can't happen at that point: module scope, Zod schema factories (recreated per render, so they pick up the current locale anyway), and the logged-out auth screens (unreachable from the in-app language switcher).

**Require-cycle rule:** import the i18n instance from `@/i18n/i18n` (the file), not the `@/i18n` barrel, in any module the barrel transitively imports — notably `src/stores/locale.ts`. The barrel re-exports `use-translate.ts`, which imports the locale store, so importing the barrel back from the store creates a `i18n → use-translate → locale → i18n` cycle. (Same reason `locale.ts` imports `@/types/bible` directly rather than the `@/types` barrel.)

**`setLocale` is the single "language changed" seam** — it does more than set `i18n.locale`, and new language-dependent behavior belongs here rather than in a screen effect:
1. persists the locale (Zustand + AsyncStorage),
2. mirrors it to Supabase `user_metadata.locale` for auth emails (see Auth flow → send-email hook),
3. **re-points the reader's Bible translation to match the new language** (`syncReaderTranslation`).

Step 3 is **conditional on purpose**: it only swaps when the current translation's `lang` differs from the new UI locale, so a deliberate same-language pick (Almeida over BibliaLivre, or a Pro-tier translation) survives a language change. It writes `useReaderStore.setState({ translationId })` **directly instead of calling `setTranslation`**, because that action also resets to Genesis 1 — correct when the user picks a translation in the reader, wrong for a UI-language switch, which shouldn't cost them their reading position (all bundled translations share the 66-book/chapter numbering, so the position stays valid). `defaultTranslationForLocale` only returns free/bundled translations, so this can never move a non-Pro user onto a gated one. **The Home "verse of the day" needs no separate handling** — it resolves its text and localized reference label through `useVerse(translationId, …)`/`useBookName(translationId, …)`, so it follows this swap automatically; its `useMemo(…, [])` pins only *which* verse was picked, which should stay stable across a language change.

### Data fetching

TanStack Query. `src/lib/query-client.ts` provides the single `queryClient` instance (provided via `QueryClientProvider` in `_layout.tsx`). Query keys are namespaced per domain as `const` objects (see `authKeys` in `use-auth.ts`) — follow that convention for new domains rather than inlining key arrays.

**Refetch on tab focus.** React Query's `refetchOnWindowFocus` is a no-op in React Native (no browser window), so a screen returned to via the bottom tabs serves stale cache and won't re-fetch on its own. For React-Query-backed screens that must reflect fresh server data on focus (e.g. the Plans list + Plan detail), call `useRefetchOnFocus(queryA, queryB, …)` (`src/hooks/use-refetch-on-focus.ts`) — it bridges expo-router's `useFocusEffect` to `query.refetch()`, refetching only **stale** queries (respecting each `staleTime`). This is the React-Query analogue of `useSyncOnFocus` (which covers the Zustand/sync-engine surfaces — Study/Reader/Home; see Sync).

### Reading progress tracking (local-first)

Defense-in-depth: app pre-check counts the **local** active enrollments (offline-capable; tier from the profile cache), a DB `BEFORE INSERT OR UPDATE` trigger on `user_reading_plans` as the server backstop (raises `PLAN_LIMIT_REACHED` on push), and the hook normalizes both into a typed `PlanLimitError`. ### Reader

Reader tab under `src/app/(tabs)/reader/` (nested `Stack`). Renders verses for the current position from `useReaderStore` (`src/stores/reader.ts`: translation/book/chapter/fontSize, persisted). Bundled offline Bible via `src/hooks/use-bible.ts` / `src/services/bible.ts`.

- **DB open must cache the promise, not the resolved DB (concurrency).** `getDb` in `src/services/bible.ts` caches the in-flight **open promise** keyed by translation, *not* the resolved `SQLiteDatabase`. The Reader fires several queries at once on mount (`getBooks`, `getVerses`, `getMaxChapter`, per-chapter highlights/bookmarks/notes…); if the cache only holds the resolved value (set after both `await`s), every concurrent call re-runs `importDatabaseFromAssetAsync` + `openDatabaseAsync` on the same file. On Android those overlapping import/open calls collide and one yields a DB with a **null native handle** → the first `db.prepareAsync` throws `NativeDatabase.prepareAsync … NullPointerException`. It surfaces on **fresh debug builds** specifically, because that's when the asset import actually runs (on a reinstall the file often already exists, so a call sometimes wins the race → intermittent). Fix: cache the promise so all callers await one open; pass `forceOverwrite: false`; and evict a rejected promise (`open.catch(() => dbCache.delete(id))`) so one transient failure doesn't permanently poison the cache. Don't "simplify" this back to caching the awaited DB.

- **Translations (free vs. Pro).** `TRANSLATIONS` in `src/types/bible.ts` carries a `tier` (`free`/`pro`) per translation; **all** are bundled SQLite (Pro is an entitlement gate, **not** a download — V1 is public-domain only, no copyrighted/modern versions; see `.docs/bible-translation-licensing.md`). `FREE_TRANSLATIONS`/`PRO_TRANSLATIONS` are derived lists. `TranslationPicker` groups them Free/Pro and, via `useIsPro()`, routes a free/guest user's tap on a Pro row to the **paywall** (`handleTranslationUpsell` → `/paywall`) instead of switching. - **Plan reading session:** opening a not-yet-done plan day from plan detail sets an ephemeral, in-memory `usePlanReadingStore` session (`src/stores/plan-reading.ts`: `userPlanId`, `day`, `bookId`, `lastChapter`, …) and navigates to the Reader. When the reader is at that session's last chapter, a **"Concluí esta leitura" footer CTA** (list footer, reachable only by scrolling through the passage) marks the day complete via `useMarkPlanDayComplete`, then shows the **`PlanDayCompleteModal`** celebration dialog (day vs. whole-plan copy via a `finished` flag + prayer nudge). This **replaced the old success toast** (the error path still toasts). The session clears on completion or when the user manually picks different content via the book picker.
- **Verse study actions (Pro only):** for **Pro** users each verse is wrapped in a `Pressable`; tapping opens the `VerseActionSheet` (highlight color picker + bookmark toggle + note action) — a `@gorhom/bottom-sheet` native sheet (see Component layers). The note action opens `NoteEditorModal`. (`handleVersePress` keeps a `!isPro` no-op guard as defense-in-depth.) See Study tools.

### Store review prompt

`src/lib/review-prompt.ts` (`maybeRequestReview()`) wraps `expo-store-review`'s native in-app rating prompt (`StoreReview.requestReview()`), gated by a persisted **once-per-install** flag (`useReviewPromptStore`, `src/stores/review-prompt.ts`, `nascente-review-prompt`) — the OS itself also throttles repeat requests, but we still gate client-side so a single install doesn't burn one of the OS's limited slots on a low-signal moment. `maybeRequestReview()` also checks `StoreReview.hasAction()` (the native API can be unavailable in dev/simulators) before marking the flag and firing. Both call sites live in `reader/use-reader-screen.ts` and are fire-and-forget (`void maybeRequestReview()`), fired at genuine high-satisfaction moments rather than app-open/random timing:

- **Whole-plan completion (Pro).** `handlePlanCompleteContinue` fires it only when `planComplete.finished` is true (the whole-plan celebration, not a single day) — asked *after* the celebration modal's Continue tap, not layered on top of it. Reuses the `finished` flag already computed by `useMarkPlanDayComplete` (see Reading plans).
- **3-day reading streak (free/guest only).** A second `useEffect` reacts to `readDays` (`useReadingProgressStore`, local-first, never gated) and fires when `!isPro && computeStreak(readDays) === 3` — an early but real satisfaction signal for readers who may never touch Pro-gated Plans. Scoped to non-Pro so it doesn't race the plan-completion trigger for the same once-per-install ask (Pro users are already covered by that one). Deliberately a separate effect from the per-chapter `markChapterRead` call so it only fires the day the streak actually advances, not on every chapter view.

Both triggers were chosen over app-open/interstitial prompts per the "progress, not pressure" plans principle (`.docs/user-flows/plans.md`) — a review ask is a reward for a goal already met, not a nag.

### Study tools (highlights, bookmarks, notes)

Three **study tools** ship today — **highlights**, **bookmarks**, **notes** — all **local-first and Pro-gated** (the Reader verse tap → paywall for non-Pro; the Study tab shows a `ProLockCard` for non-Pro). These are separate from the AI study tools (Explain/chapter-summary/devotional — see "AI study tools" below); word study and Ask/go-deeper are still deferred. Bookmarks and notes are deliberate clones of the highlights architecture; each follows the same five-part pattern: typed identity + key in `src/types/study.ts` → persisted per-user Zustand store → hooks in `src/hooks/use-*.ts` → an action in `VerseActionSheet` → an enriched entry in the Study tab. Architecture mirrors reading-progress (on-device now, sync later).

- **Types:** `src/types/study.ts` — `Highlight` (+ `HighlightColor`, palette keys match `theme.highlights`), `Bookmark` (plain per-verse toggle, no body), `Note` (`body: string`), each with a `<thing>Key(userId, bookId, chapter, verse)` helper. Verse reference is the canonical identity; `translationId` records origin.
- **Stores:** `src/stores/{highlights,bookmarks,notes}.ts` — persisted Zustand, `byKey: Record<string, T>` keyed per **user+verse** so accounts on one device never collide. Persist names `nascente-{highlights,bookmarks,notes}`. (Highlights upsert preserving `createdAt`; bookmarks are an idempotent add/remove; notes upsert a `body`.)
- **Hooks:** `src/hooks/use-{highlights,bookmarks,notes}.ts` — each exposes `useCurrentUser<T>()` (filters `byKey` by `user.id`; empty for guests), a per-chapter selector (`useChapterHighlights` → color map, `useChapterBookmarks` → `Set<number>`, `useChapterNotes` → `Record<number, Note>`), and `use<T>Actions(translationId)` (writes are **no-ops without a user id**). Selectors filter by current user, so **logout instantly shows nothing** — no cross-user leak.
- **Verse action sheet** (`VerseActionSheet`, a gorhom bottom sheet): one surface for all per-verse actions — the highlight color picker (6 + remove), a **bookmark** toggle (toggles in place, sheet stays open), and a **note** action that closes the sheet and opens the `NoteEditorModal`. Wired in `reader/use-reader-screen.ts` (gated to signed-in; `handleVersePress` returns early for guests).
- **Note editor:** `NoteEditorModal` (organism) — a centered dialog on `AppModal` with a multiline field + save/delete; the Reader remounts it per verse via a `key` so it initializes from the existing note body without a reset effect.
- **Study tab** (`src/app/(tabs)/study/`, nested `Stack`): **non-Pro users get a `ProLockCard`** (→ `/paywall`); Pro users get a `SegmentedControl` filter (Tudo / Destaques / Notas / Marcadores) over one unified list of `StudyItem`s. `use-study-screen.ts` merges all three annotation types and **enriches** them with book name + verse text from `@/services/bible` via one `enrichItems` pass (verses/book name fetched once per unique translation+book+chapter), sorted canonically. The React Query key is built from item identities **including note body** so it refetches on add/remove/edit. Tapping an item sets the reader position + navigates. The **4th bottom-nav tab** ("Estudo") in `(tabs)/_layout.tsx`. The filter now **defaults to `'highlights'`** (the first segment) rather than the segment-less `'all'`, so a segment is always selected on load. When a filter has no items the list renders the **`StudyEmptyState`** organism (icon-badge + title + description + Secondary/outlined CTA → reader, modeled on `ProLockCard`'s shape but a static `Card`); per-tool icons are `Highlighter`/`NotebookPen`/`Bookmark` (mirroring the reader's `VerseActionSheet`), and copy is `study.empty.{highlights,notes,bookmarks}.{title,description,action}` (per-filter objects, all three locales).
- **Sync:** the local stores mirror to Supabase (`highlights` / `notes` / `bookmarks`, now LIVE) when signed in + online — see Study tools sync below. Guests stay fully local (no network writes); the stores remain the on-device source of truth.

### AI study tools (Explain, chapter summary, devotional, prayer, AI plans)

The scripture-keyed AI features ship today, Pro-gated: **Explain** (+ its "explain like I'm new" variant), **chapter summary**, a **devotional** reflection, and a **prayer prompt**. All are **scripture-keyed** (same passage → same output for everyone) and served through a **shared server-side cache** — see `.docs/ai-features.md` for the full cost model. There's also the user-keyed **AI plan generator** (see the Reading plans section). Word study and Ask/go-deeper are deferred to V2.

- **UI:** `AiExplainSheet`, `ChapterSummarySheet`, `AiDevotionalSheet`, `AiPrayerSheet` (`src/components/organisms/`) — `@gorhom/bottom-sheet` sheets following the same conventions as `VerseActionSheet` (force-close on blur via `useFocusEffect`, un-`withUnistyles`'d per the Reanimated/BottomSheet pitfall in the Styling section). Explain/prayer are opened from `VerseActionSheet` per-verse actions; chapter summary from `ChapterNavBar`; devotional from the Home Verse-of-the-Day card.
- **Types:** `src/types/ai.ts` — `AiPromptType` (`'explain' | 'explain_simple' | 'chapter_summary' | 'devotional' | 'prayer_prompt'`), `AI_PROMPT_VERSION`, `aiCacheKey(...)`. `AiGenerateErrorCode` includes `COST_CEILING_REACHED`.
- **Prompt version (cache invalidation).** `AI_PROMPT_VERSION` is a **cache-invalidation token** — it's part of `aiCacheKey`, so bumping it makes previously cached results unreachable and forces regeneration. **Bump it whenever an `ai-generate` `systemPrompt` changes.** It's **duplicated in two places that must move together**: `AI_PROMPT_VERSION` in `src/types/ai.ts` (client's local cache key) and `PROMPT_VERSION` in `supabase/functions/ai-generate/index.ts` (server's `ai_cache` row key). The app/Deno split means there's no shared import — bump BOTH by hand or the client and server key on different versions (client stores under vN, server serves vN+1 → the local cache never hits). **Only `ai-generate` has a prompt version**, and that's correct, not an oversight: it's the only function with a persistent cache (`ai_cache`). `ai-plan-generate` persists nothing (free-text topic input isn't cacheable) and `revenuecat-webhook` isn't an LLM function — neither has a cache to invalidate, so a version constant there would be dead code. A prompt/logic change to `ai-generate` also needs a **redeploy** (`supabase functions deploy ai-generate`) — until then the old function ignores new request fields and keys on the old version.
- **Backend:** `supabase/functions/ai-generate/index.ts` (Deno, `@ts-nocheck`, excluded from the app tsconfig) — verifies JWT, checks `profiles.tier === 'pro'`, checks the per-user **cost ceiling** (`ai_usage`, ~$1.50 / 30-day cycle), checks the shared `ai_cache` (returns hits at $0, exempt from quota), else calls the model, upserts to `ai_cache`, and **increments `ai_usage`** (cache misses only). **Model is Gemini 2.5 Flash** (`GEMINI_MODEL` const) — `ai-features.md` recommends Claude Haiku 4.5; the shipped code diverges, so don't trust the doc's provider/pricing numbers without checking the function.
- **Metering (built).** `ai_usage` (per-user dollar cost ceiling) and `ai_plan_usage` (per-user AI-plan count, 10/cycle) are LIVE, incremented via `increment_ai_usage` / `increment_ai_plan_usage` RPCs. The cycle is a **30-day rolling window anchored to `profiles.pro_since`** (set by the RevenueCat webhook on the free→pro transition), computed in-Edge-Function (`currentCycleStart`, deliberately a fixed 30-day window not a calendar-month anniversary — see the comment there). Scripture-keyed features only meter the cost ceiling; AI plans meter both counters. Quota numbers (100 explain / 50 Ask / 10 plans / 10 narrations) are documented in `../.docs/product-spec.md`; the paywall copy lists AI *tools*, not numbers (deliberate — see `ai-features.md` §3). Ask/go-deeper's own per-feature counter is not built (deferred with the feature).
- **First-time AI feature tours.** `@wrack/react-native-tour-guide` (`TourGuideProvider` + `TourGuideOverlay` mounted once at the root of `src/app/_layout.tsx`) spotlights each AI action the first time a Pro user encounters it, via `useTourPersistence(AsyncStorage)` — the library's own "show only once" persistence, not a custom Zustand store (unlike `review-prompt.ts`, which predates this and hand-rolls the same thing). Chose this library over `react-native-copilot` for two reasons: it's actively maintained (June 2026 vs. `copilot`'s Dec 2024, pre-dating RN 0.86/New Arch) and has **zero Reanimated/gesture-handler dependency** — this codebase has been burned repeatedly by Reanimated-based libraries breaking on the Expo 57/RN 0.86 upgrade (see the Reanimated section), so a tooltip lib built on the same internals would be a fifth thing to eventually hit that class of bug. **`Button` (pressto's `PressableScale`) doesn't forward refs** — every target ref in these tours is attached to a plain wrapping `View` around the targeted `Button` instead, since the library's `measureInWindow`-based measurement needs a real host-component ref (see `VerseActionSheet`'s `styles.actionFill`, `ChapterNavBar`'s summary-button wrapper, `VerseOfTheDayCard`'s existing `devotionalButtonWrapper`). Three separate tour instances, each its own `tourId` (so dismissing/completing one doesn't affect the others) and its own trigger shape depending on how the target becomes visible:
  - **`ai-features-reader`** (`reader/use-reader-screen.ts`, `handleVersePress`) — spotlights the Explain/Prayer buttons inside `VerseActionSheet`, tap-triggered (fires when the sheet opens). **Targets live inside a `@gorhom/bottom-sheet`**, which isn't officially documented as supported by this library — `TourGuideOverlay` renders in its own native RN `Modal` (confirmed by reading the library's source, not just its docs) so it paints above the sheet regardless, and the first step's `delayBefore: 400` gives the sheet time to finish its open animation before the library measures the target. **Verified working on-device.**
  - **`ai-features-home`** (`use-home-screen.ts`) — spotlights the devotional button on `VerseOfTheDayCard`, mount-gated (a `useEffect` firing once `isFocused && isPro && !verseLoading && verseText` — the button is always visible on Home, not opened on demand, so there's no tap gesture to hang the trigger off of).
  - **`ai-features-chapter-summary`** (`reader/use-reader-screen.ts`) — spotlights the summary button in `ChapterNavBar`, same mount-gated shape (`isFocused && isPro && !isLoading && verses?.length`) as the Home instance, since that button is also always visible rather than opened on demand.
  - **Mount-gated triggers MUST also gate on `useIsFocused()` (`expo-router`'s re-export)** — a real bug hit here: `NativeTabs` keeps every tab screen mounted in the background for instant switching, so a `useEffect` gated only on data-readiness (`isPro && !isLoading && ...`) fires as soon as that data loads **regardless of which tab is actually visible**. Since `TourGuideOverlay` is a root-level `Modal`, the spotlight then renders on top of whatever screen the user is *actually* looking at — e.g. the Reader's chapter-summary tour appearing while on the Home tab, because the Reader was still mounted in the background and its chapter data finished loading. The tap-triggered `ai-features-reader` tour above is immune (a verse tap can only happen on a screen the user is actually viewing), but any **new mount-gated** tour needs the same `isFocused` guard these two now have.
  - All effects list `startTour`/`translate`/`isFocused` as real dependencies rather than reaching for an `eslint-disable` — a bare `react-hooks/exhaustive-deps` suppression trips **`react-compiler/react-compiler`**, which refuses to optimize a component containing a suppressed React-rules lint (see the same note under "Auth-callback deep links" above).

### Sync (offline-first)

Local-first user data syncs to Supabase via a layer **on top of** the AsyncStorage Zustand stores (the stores stay the local source of truth — this is **not** a SQLite migration; unifying persistence on SQLite is a future TODO in `.docs/notes.md`). Two models: the **study tools** (highlights/bookmarks/notes — LWW + tombstones) and **reading-progress** (append-only set-union). The engine lives in `src/services/sync/` and is mounted once by the headless `useSync()` hook (`src/hooks/use-sync.ts`) in `src/app/_layout.tsx`. Full design + diagrams: `.docs/study-tools-sync.md`.

- **Row sync metadata.** Each record (`Highlight`/`Bookmark`/`Note`) carries `SyncMeta` (`src/types/study.ts`): `updatedAt` (LWW key), `deletedAt` (tombstone), `dirty` (local change not yet pushed), `syncedAt`. **Deletes are soft** — `remove*` keeps the row and stamps `deletedAt`+`updatedAt`+`dirty` (so the delete syncs); writes clear `deletedAt` (un-tombstone) and set `dirty`. Selectors in `use-{highlights,bookmarks,notes}.ts` filter out tombstones, so the UI/Study-tab/Home count ignore them. **Bulk "clear all"** is a **per-type** action — a **list-footer** button on each of the three specific Study tabs (Highlights / Notes / Bookmarks), **not** on the mixed "All" tab (a single clear-all there would be ambiguous) → confirm `AppModal` → `clearAll{Highlights,Bookmarks,Notes}(userId)` on the matching store → the shared `softDeleteAllForUser` helper (`store-helpers.ts`), the batch analogue of `remove*`: it tombstones every live row for the user in one pass (never a hard wipe), so the deletion syncs. The store writes are reactive (the `useCurrentUser*` selectors re-derive), so the list refreshes on its own; the handler just fires `syncAll(userId)` to push the tombstones. The hook exposes `clearFilter: ClearableFilter | null` (the active clearable type when its list is non-empty, else null) — this both gates the footer/modal and narrows the i18n key off `'all'` so `clearAll.*.${clearFilter}` type-checks. (Bookmarks gained an `updatedAt` for this; a one-time `migrateSyncMeta` on rehydrate backfills legacy rows + marks them `dirty` so the existing local corpus uploads on first sync.)
- **Engine (`src/services/sync/`).** One generic `syncCollection<T>(descriptor, userId)` drives all three study tables (they share the verse-identity shape) via a `CollectionDescriptor` (table name + `toRemote`/`fromRemote` mappers + store seams). `run.ts`'s `syncAll(userId)` runs the three study collections **plus** reading-progress sequentially with an in-flight guard + queued re-run (overlapping triggers don't stampede). The store seams `applyPulled`/`applyPulledMany`/`markSynced` + the shared merge/prune helpers live in `store-helpers.ts`.
- **Push then pull.** Push first: upsert `dirty` rows (chunked) on `onConflict: 'user_id,book_id,chapter,verse'` (idempotent on verse identity), read back the server `updated_at`, and `markSynced` (clears `dirty`, re-anchors `updatedAt` to server time). Then pull: rows where `updated_at > cursor` (per-collection-per-user cursor in `useSyncMetaStore`, persist `nascente-sync-meta`), paginated, cursor advanced to the max **server** `updated_at` seen (resumable backfill). Push-before-pull means our own rows echo back as LWW ties (no flicker).
- **Conflict rule (LWW).** A pulled row wins **iff `incoming.updatedAt > local.updatedAt`** (else keep local; ties keep local). Because a write clears `deletedAt`, this one rule resolves edit-vs-edit, delete-vs-edit, and resurrect by newest server timestamp. `updated_at` is **server-authoritative** (column default + the `set_updated_at` BEFORE UPDATE trigger override any client value), which is the clock-skew mitigation.
- **Reading-progress (append-only).** `src/services/sync/reading-progress.ts` syncs `readChapters`+`readDays` with a simpler model — no tombstones/LWW/cursor. Push inserts the whole local set (`on conflict do nothing`); pull unions all rows in via the store's `mergeRemote`. The store is **device-global**, so a guest's progress unions up to the account on sign-in. See Reading progress tracking above + `.docs/study-tools-sync.md` §9.
- **Reading plans.** `src/services/sync/reading-plans.ts` syncs three local stores (catalog pull-only → enrollments status-merge LWW → completions append-only union; run in that FK order). Backs the offline-first `use-reading-plans.ts` hooks (see Reading plans). Because those hooks read store *snapshots* via React Query `queryFn`s (not reactive), `useSync` **invalidates `planKeys`** when a plan store changes (local write or pull) so the Plans screens re-derive. See `.docs/study-tools-sync.md` §11.
- **Triggers.** `useSync` (`use-sync.ts`) runs only when the stores + auth are hydrated AND a user is signed in (guest no-op). Fires on: sign-in / user-id change (also launch-with-session), app foreground (`AppState`), reconnect (`@react-native-community/netinfo` false→true edge), and a debounced local mutation (study `byKey`, reading-progress, or the plan stores). A separate `useSyncOnFocus` (same file, via `useFocusEffect`) pulls when a screen gains focus — mounted on the **Study tab**, **Reader**, **Home**, and **Plans** (list + detail) so an in-app tab switch re-pulls another device's changes (a tab switch does **not** fire `AppState` foreground). **Logout** (`useLogout`) calls `useSyncMetaStore.clearForUser(previousUserId)` so a re-login does a clean full re-pull; the per-user stores stay untouched (they filter by user id, so logout shows nothing) and any un-pushed `dirty` rows flush on next sign-in. (The catalog store is device-global — not cleared.)
- **Schema + purge.** The study tables + `user_reading_progress` are LIVE (`.docs/data-model.md`). Study tombstones are purged at a **90-day** retention window both server-side (`purge_study_tombstones` via the `purge-study-tombstones` `pg_cron` job, daily) and client-side (`pruneTombstones` on rehydrate, only dropping already-pushed tombstones).

### Analytics (PostHog)

Product analytics, session replay, error tracking and structured logs, plus **server-side AI observability** in the Edge Functions. Four PostHog products are enabled: **Product Analytics, Session Replay, Error Tracking, Logs** (+ LLM analytics via `$ai_generation`). **Feature flags/experiments are deliberately NOT set up** — nothing consumes a flag yet.

- **Seam:** `src/lib/posthog.ts` is the single entry point, modelled on `lib/revenuecat.ts` — module-level key from `process.env`, a `configurePostHog()` called once at module scope in `src/app/_layout.tsx` (right beside `configureRevenueCat()`), and **every helper no-ops without a key** so a fresh clone/CI boots analytics-free. Nothing else imports `posthog-react-native` except the two `PostHogMaskView` call sites. Exports `capture`/`screen`/`identifyUser`/`resetIdentity`/`registerSuperProperties`/`captureError`/`log`.
- **Typed events:** `src/types/analytics.ts` holds an `AnalyticsEventMap` (event name → properties); `capture()` is generic over it, so a typo'd event name or a missing property is a **build error**. Add new events there first. Event names are `snake_case` past-tense (`plan_started`); renaming one splits its history in PostHog.
- **⚠️ Screen tracking is MANUAL and must stay that way.** PostHog's `captureScreens` autocapture does **not** support `@react-navigation/native` v7+ (this app is on 7.3.5 via expo-router), so the provider sets `autocapture={false}` and `src/hooks/use-analytics.ts` captures screens from **`usePathname()`**. Do not "fix" this by enabling `captureScreens` — it silently produces nothing. `autocapture={false}` also disables `captureTouches` **by decision**: the app instruments named events at handler seams, and generic `$autocapture` would both add noise and risk capturing note/verse text via element labels.
- **⚠️ `usePathname()`, not per-screen mount effects.** `NativeTabs` keeps every tab mounted in the background, so a mount/data-ready `useEffect` fires for tabs the user never looked at (the same trap that made the AI tour spotlight appear on the wrong tab). `usePathname` changes only on real navigation, so one effect covers every screen with no `useIsFocused` gating to forget. The one analytics effect that *does* live in a screen — `chapter_read` in `use-reader-screen.ts` — is explicitly gated on `isFocused` for this reason.
- **Identity:** `syncPostHogIdentity(userId)` in `src/stores/auth.ts`, sitting beside `syncRevenueCatIdentity` and called from the same three lifecycle sites + `useLogout`. Its **synchronous `lastPostHogUserId` guard** is required: `onAuthStateChange` re-fires on every token refresh, and re-`identify()`ing each time would write a person profile per refresh. The distinct id is the Supabase `auth.users.id` — deliberately the same id RevenueCat uses as `app_user_id` **and** the Edge Functions use for `$ai_generation`, so product events, revenue and AI cost all join to one person.
- **Super properties** (`use-analytics.ts`): `is_pro`, `is_authenticated`, `app_locale`, `translation_id`, `theme` ride on every event, so segmentation doesn't need per-event properties.
- **`useProGate().openPro(source)` is the upsell funnel's single chokepoint** (`src/hooks/use-profile.ts`). It captures `pro_gate_hit` with the source, so all six Pro-gated surfaces are attributed from one call site. **New Pro gates must go through `openPro`**, not `router.push('/paywall')`, or they're invisible in the funnel. Note the `source` param means a bare `handleUpgrade = openPro` alias would pass the press event as the source — wrap it (`useCallback(() => openPro('x'), [openPro])`).
- **🔒 Privacy rule (no automated backstop — enforce it in review):** never capture verse text, note bodies, search queries, AI prompts/completions, emails or names. Send **lengths, counts, ids and enums** instead (`note_saved` sends `body_length`; `ai_plan_generated` sends `has_topic`, not the topic).
- **AI events are captured inside `useAiGenerate`'s `queryFn`, and that covers cache hits too.** The sheets mount with `enabled: false` and flip true when opened, so opening an already-cached passage still runs the query rather than resolving synchronously from `initialData` — verified on-device for both a fresh and a cached chapter summary. Don't add a second capture in a `useEffect` to "catch" cache hits; it would double-count every hit. `prompt_type` is what distinguishes the five AI tools (`explain`, `explain_simple`, `chapter_summary`, `devotional`, `prayer_prompt`) in every AI event, client and server.
- **Session replay masking:** `maskAllTextInputs`/`maskAllImages` are on globally, but that only covers `TextInput`s — **a note body rendered as `<Text>` is NOT masked**. `NoteEditorModal` (the input) and `StudyCard` (the note preview) both wrap their note content in **`PostHogMaskView`** explicitly. Any new surface that renders a note body needs the same wrapper.
- **`disabled: __DEV__`** keeps local development out of production data. Flip it temporarily to verify against PostHog's live Activity feed.
- **Native module:** `@posthog/react-native-plugin` (native crash capture) is autolinked — **no `app.json` plugin entry**, but it does need a native rebuild, like RevenueCat/Google-Signin.
- **AI observability lives SERVER-SIDE** (`supabase/functions/_shared/posthog.ts`, used by `ai-generate` + `ai-plan-generate`), because tokens/latency/cost only exist where Gemini is actually called — the client never sees them. Uses `posthog-node` and PostHog's **manual `$ai_generation` schema** (Gemini has no first-party wrapper). Only cache **misses** reach it, which is correct: a hit is free and isn't a generation. Key points:
  - **Every path must `await flushPostHog()` before returning.** Edge isolates freeze after the response, so buffered events are dropped **silently** — no events, no error. This is the most common way the integration breaks. The client is created per-invocation with `flushAt: 1`/`flushInterval: 0` for the same reason.
  - **`$ai_input`/`$ai_output_choices` are deliberately omitted** — they'd ship the scripture passage and generated devotional text to PostHog. Cost/latency/error analysis doesn't need them.
  - Cost is derived by PostHog from model + token counts; the function's own `callCost` remains the authority for the `ai_usage` ceiling. `prompt_type` is sent as a custom property so spend can be attributed per AI feature — the thing `ai_usage` alone can't tell you.
  - Secrets are separate from the app's: `supabase secrets set POSTHOG_API_KEY=... POSTHOG_HOST=...` (**same project key** as the app — that's what makes the join work), then redeploy both functions.
- **Env:** `EXPO_PUBLIC_POSTHOG_API_KEY` (public `phc_…` write-only key) + `EXPO_PUBLIC_POSTHOG_HOST`. The host is the project's **region**, not a settings field — this project is **EU Cloud** (`https://eu.i.posthog.com`) for pt/es data residency. A project's region cannot be changed after creation.

## Conventions

- ESLint config (`eslint.config.js`) is `eslint-config-expo` flat config + Prettier + `eslint-plugin-react-compiler` (recommended ruleset is enforced — write components compatible with the React Compiler, e.g. no manual memoization workarounds it would conflict with).
- Prettier: single quotes, semicolons, 120 print width, ES5 trailing commas, LF line endings (`.prettierrc`).
- Components/hooks/services follow named exports (no default exports except Expo Router screens, which require default export, and their co-located screen-private hooks — see "Route folders with co-located logic" above).
